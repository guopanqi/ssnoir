## 2026-10-03 — Hero / Context / Silence

**问题**

普通街屋的轮廓线是否真的帮助空间阅读，还是把背景重新拉回前景。

**固定条件**

四个 benchmark 镜头、几何、主光、空气和 Print 均保持不变。

**变量**

普通街屋主体从 Context 改为 Silence；剧院、仓库和后巷连桥继续保留 Hero，少数结构细节保留 Context。重新加入轻量 Line 诊断。

**观察**

- 01 剧院：Hero 线仍明确强调剧院，普通街屋消失的结构线没有破坏街道纵深。
- 02 仓库：仓库屋顶与主体轮廓仍可读，远处街屋更安静。
- 03 后巷：连桥仍是唯一明显结构线之一，前景黑块没有被重新勾亮。
- 04 城市压缩：街屋不再形成连续白边，建筑层级更依赖明暗面和 silhouette。
- Shape → Line 的平均亮度变化在四镜头中约为 +0.001 到 +0.002，说明线层开始从“全局滤镜”退回为稀疏的信息层。

**结论**

- 保留：Hero / Context / Silence 三级语义，其中 Silence 是正式的一等状态。
- 放弃：普通背景建筑默认描边。
- 尚不确定：Context 的 0.11 opacity 是否还可继续降低，暂不调整。

**原因**

线仍能帮助关键物件被识别，但背景不再因为几何边缘本身而获得视觉优先级。这样更符合“显示什么与不显示什么同样重要”的 Noir Engraving 原则。

**迁回 Unity**

CityBox 资产应允许显式的 line importance / outline mask，而不是统一屏幕空间 Outline。Hero、Context、Silence 应由叙事和构图层级决定。


## 2026-10-03 — 低角度侧后主光

**问题**

全局主光是否可以减少道路亮面积，同时保留建筑垂直面的可读性。

**固定条件**

四镜头、几何、线层、仓库/后巷叙事光和 Print 均不变。

**变量**

主光从较高的 [-42, 30, -28] 改为更低的 [-44, 17, -30]，强度不变。

**观察**

- 01 剧院：道路明显退暗，建筑侧面仍保持层级。
- 02 仓库：Final 中 bright>20% 从约 38.3% 降至 25.4%，此前抢眼的道路亮面缩小，仓库工作区仍可读。
- 03 后巷：由于灯光层隔离，几乎不受影响，证明叙事光隔离有效。
- 04 城市压缩：水平面更黑，明暗带更接近街道峡谷，而不是均匀照亮的城市模型。

**结论**

- 保留：更低、更掠射的全局侧后主光。
- 放弃：让全局 Key 以较陡角度同时照亮道路和建筑。
- 尚不确定：是否还需要进一步把 Context 建筑从全局 Key 中分层隔离。

**原因**

在相同强度下，降低入射角自然减少水平面的受光，同时加强垂直面的方向感。这比单独压暗道路材质更接近可迁移的摄影规律。

**迁回 Unity**

优先从 Directional / large-area key 的方向关系控制水平面与垂直面的受光比例，而不是依赖后处理压暗地面。


## 2026-10-03 — 稀疏叙事色墨

**问题**

Noir Print 是否应该把所有叙事色都压成冷白，还是允许极少量暖色 / 红色穿透。

**固定条件**

四镜头、几何、线层、灯光、空气、黑白归一化、有限色阶与 Dither 均不变。

**变量**

Print 在冷色 ramp 之后增加严格的色度门控：只有源画面中确实具有明显红色或暖黄色偏向、且亮度处于可读区间的像素，才混入少量 red / warm ink。

**观察**

- 01 剧院：竖牌重新保留暗红色，入口与极少数灯点保留暖色；建筑和雨仍保持冷色版画。
- 02 仓库：主体几乎不受影响，只留下很少的暖色灯点，没有出现整体彩色化。
- 03 后巷：远端门从冷白恢复为唯一暖色目标，近中景仍保持黑蓝。
- 04 城市压缩：红色剧院牌与少数暖窗可作为远距离定位点，其余城市保持冷色。

**结论**

- 保留：经过色度门控的少量叙事色墨。
- 放弃：Final 阶段把红牌、暖门等叙事信号统一压成冷白。
- 尚不确定：不同剧情状态是否需要动态更换色墨配额，留到 Narrative Image 阶段。

**原因**

色彩不是环境装饰，而是稀缺的信息资源。只允许极少数有理由的物件穿透 Print，可以保留版画统一性，同时让叙事亮点拥有与冷白高光不同的语义。

**迁回 Unity**

SSNoirStylize 可在最终冷色量化之后增加受 mask / chroma gate 控制的 narrative ink 通道；不应恢复通用全彩材质。


## 2026-10-03 — 放弃 Three.js Layers 作为 Light Linking

**问题**

能否像 Unity Light Layers 一样，用 Three.js Object3D Layers 让全局 Key 不照普通 Context 建筑。

**固定条件**

镜头、材质、Print、灯光强度与方向均保持不变。

**变量**

新增 CONTEXT layer；普通街屋 / skyline 只放入该层；相机、fill 和 ambient 启用 CONTEXT，而 key 不启用。

**观察**

- 01–04 的 Shape / Line / Preprint / Final 视觉结果与上一轮相同。
- report 中所有主要亮度统计与上一轮相同到当前精度，说明这个改动没有改变物体的实际受光。
- 因此此前把 WAREHOUSE / ALLEY Object3D Layers 当作“叙事光隔离”的解释也不能继续成立。

**结论**

- 保留：叙事光必须有明确作用域这一视觉原则。
- 放弃：在 Three.js WebGLRenderer 中把 Object3D Layers 当作 Light Linking / Light Layers。
- 下一步：实验室用有限距离、有限锥角和真实遮挡实现局部叙事光；迁回 Unity 时再映射到 Rendering Layers / Light Layers。

**原因**

实验结果没有产生任何图像差异，而且 Three.js 的 Layers 公共契约是相机可见性 / 射线过滤，而不是材质受哪盏灯影响。代码层面的“看起来被分组”不能替代实际截图验证。

**迁回 Unity**

这一结论不否定 Unity 的 Light Layers。它只说明 Three.js 实验不能用 Object3D Layers 模拟同一机制；迁移时应使用 Unity 原生灯光分层。

## 2026-10-03 — 后巷：远置摄影光与真实遮挡

**问题**：交接版本的局部灯虽然使后巷可见，但 Final 两侧墙形成巨大白色弧形，中景不再服务远端门。

**固定条件**：四镜头、材质、主 Key、Print 和背景线策略保持不变。先审阅 artifact 11274632881，再用本地 Chromium headless shell 复现。

**变量**：摄影灯位置、目标、锥角、距离、强度；局部 lift 从 90 降到 12；巷口增加服务顶棚作为真实遮挡。最后把摄影灯沿照射轴移远，保持覆盖范围，减少墙面的圆弧明暗带。

**四镜头观察**：01 剧院主体层级保留；02 仓库没有重新出现成片被提亮的邻近屋顶；03 黑色巷口、冷色中景墙和暖门成立，平台与顶棚阴影读作结构，地面出现有限亮路；04 城市没有回到均匀照亮的状态。早期较宽锥角曾提亮 02/04 两处屋顶，已放弃该配置。

**结论**：保留远置有限锥角 Spot 与真实建筑切光。放弃靠近可见墙面的高强度灯、过宽作用域以及旧全城 DirectionalLight。移远之前的稳定阶段后巷 bright>20% 从基线 26.2% 降到约 3.5%；最终整合版本为 2.7%，black<2% 为 84.2%。

**原因**：单改锥角不能去掉近光源的距离衰减轮廓。把灯沿光轴移远后，墙面受光更均匀，主要亮区边界可以交给顶棚和平台；暖门因此重新获得权重。灯不是 diegetic 物件，仍使用真实三维光照与阴影。

**迁回 Unity**：制作“遮蔽巷口 + 单侧中景摄影光 + 暖门”的场景模板；使用真实遮挡和 Unity 灯光分层。Three.js 的强度数字不直接迁移。只验证了固定镜头，不宣称任何自由机位都成立。

证据：`captures/reviews/2026-10-03-local/baseline/`、`accepted-alley/` 与最终 `final/03-alley-mouth.png`。

## 2026-10-03 — 城市长焦镜头与地标内部线层级

**问题**：04 的飞塔被画面上缘截断，黑色飞塔外缘的 Hero 白线变成过大的空线框。

**固定条件**：后巷的稳定照明、城市几何、材质、主光、空气和 Print。

**变量**：04 机位从 [72,12.5,1.5] 改为 [72,9.5,2.5]，目标从 [2,5,-1] 改为 [2,7,-9]；FOV 保持 30。剧院飞塔由 Hero 改为 Context，入口建筑与雨棚保持 Hero。

**四镜头观察**：01 的亮侧面、红牌与入口仍能辨认，飞塔体量不依赖白框；02 与 03 的空间层级不变；04 飞塔不再被上缘截断，红牌与入口更靠近阅读中心，前景遮挡保留，飞塔白线框消失。

**结论**：保留。地标内部也应分配线的重要性，不必整栋建筑统一 Hero。构图变化意味着新旧 04 的黑面积不能被当作纯渲染参数的提升。

**原因**：线的语义应该指向需要阅读的入口与结构；高大的辅助体量可以依靠 silhouette 和亮侧面成立。

**迁回 Unity**：CityBox / 地标模型应允许部件级 line importance；镜头明确为入口与地标标点留出位置。

证据：`captures/reviews/2026-10-03-local/framing/`。

## 2026-10-03 — 雨退到空气层，以及本地循环

**问题**：全尺寸 04 中雨线在黑底上成为大量亮标记，与结构线争抢阅读。

**固定条件**：已保留的构图与部件线策略、同一 seed、同一雨滴数量、雾和 Print 参数。

**变量**：rainOpacity 0.12 → 0.055；rainLength 0.90 → 0.65。

**四镜头观察**：01 的入口与红牌、02 的工业轮廓和窗光仍优先；03 保留稀薄空气，没有抬灰近景；04 的雨仍可察觉，但大片长白线显著退后。未加入新空气效果。

**结论**：保留较弱且较短的雨。受光选择性的雨、遮蔽区不落雨以及自由机位时的近处雨长度仍未验证，留到后续 Atmosphere 研究。

**迁回 Unity**：先校准雨在最终 Print 之后的显著程度，不能只在 Preprint 中判断 opacity；雨应低于交互点和结构线。

**循环改进与验证**：本地支持 --shot、--mode、--out、--port 和 --help；16 图完整截图约 14–18 秒，单图运行约 5 秒，省去逐轮 Actions 排队、上传和下载。保留四列诊断、源码 SHA-256、完整 profile 与浏览器版本。临时在 setShot 注入 console error，任务约 5.1 秒失败；恢复后 build 与截图成功。截图成功必须包含实际打开图片检查。

最终证据与阶段比较：`captures/reviews/2026-10-03-local/`。

**CI 补充**：提交后的 runner 完整 Chrome 首次因资源 404 被严格错误检查中断（run 37129033888）。页面新增明确的空 favicon 声明，避免隐式图标请求；HTTP 错误现在记录状态码与 URL，console error 记录来源。保留资源失败即中断的规则，不把 404 一概忽略。


## 2026-10-04 · 住所实验（独立入口）

问题：已认可的桥头“描线与块面”能否用于普通公寓和侦探租屋？
固定：复用桥头最终明暗 shader，曝光 1.25，确定性程序化几何，不新增全屏效果。
变量：空间布局、建筑形体、局部光源与结构线密度。用户要求换成住所，所以采用该实验的四个机位，而非原街区的剧院/仓库镜头。

四镜头观察：
- 公寓街角：凸窗、檐口和入口能组织主楼，邻屋窗框偏亮，后续可弱化背景线。
- 入口：台阶与栏杆可读；修正半圆雨棚的轴向，避免读成竖立圆片。
- 室内全景：床与书桌分区明确，中央地面保留空地，窗格投影和阅读灯形成两个亮区。
- 书桌近景：收紧相机距离后能读出打字机、纸和椅子；灯光在墙上的环状色阶仍偏明显。

保留：共用明暗映射；按职责建立物体轮廓；窗光投影与局部灯光。
尚不确定：邻屋窗线密度、室内墙面色阶、刻线是否需要保留。待用户审图；没有将候选定为全游戏规范。
迁回 Unity：复用布局和几何职责，重建明确描线层与光源，独立实现相同的亮度映射，检查锚点投影；当前未执行迁移。

验证结果：住所与桥头独立 Vite 构建均成功（有超过 500 kB 的 bundle 体积提示，无构建错误）；住所四个机位实际渲染并截图；受光/刻线按钮与机位链接导航已实际操作；住所和桥头控制台未发现 error。未验证 Unity 或手机性能。


## 2026-10-04 · 黑水（城市视角，独立入口）

问题：桥头 / 住所研究的是**一个空间**怎么被照亮。城市视角（上千米外、上千栋楼）是另一个问题——
现行全城机位把城市画成深蓝底上的白色线框，每栋楼同等对待、每根边同样亮，读起来是图纸不是夜。
这一轮只回答：**城市尺度的黑色电影，靠什么把形体从黑里读出来？**

固定：真实城市几何（CityBox 构建产物烘焙成快照，1275 栋填充楼 / 3430 扇窗 / 63 万三角面），
七个固定机位，四个阶段分层（体块 → 空气 → 描线 → 成片），全部自写 ShaderMaterial。

变量：体块反照率与冷键的性质（泛光 → 镜面高光）、描线的亮度来源、
暖池的数量与高度衰减、反射的适用范围、空气的绝对量级、成片的密度控制位置。

七机位观察：
- 世界机位：改成"极弱冷底线 + 强背景依赖 + 朝向冷键调制"之前，每栋楼都闭合描边，整座城退回线框图。
- 隔河长焦：冷键改成镜面高光后，黑牌楼上只剩窗和一个朝向的银边，这是本轮最像 noir 的一格。
- 河上北望：水面是黑的镜子，"水在前、城在后"成立；近岸空地仍偏平。
- 码头低角：低机位湿地面反转有效，但机位名不副实，码头那条带被前景挡住。
- 雨夜：一条 `uRainAmount` 同时驱动雨丝与涟漪强度，雨夜读起来是统一的。
- 逆光剪影：月晕从 `pow(m,3)` 收到 `pow(m,260)` 之前，整片天被照亮，城市反而不是剪影。
- 高处俯瞰：城市像一块被光刻过的电路板；这是四阶段分层最有说服力的一格。

保留：冷键用镜面高光而非泛光；描线亮度 = 背景光 × 朝向冷键；灯光的高度衰减 `exp(-(y-灯高)/16)`；
受限色阶只在**显示域**做、且只量化亮度；雨量与雾/反射由一条 uniform 耦合。
放弃：全城烘焙描线（每边等亮）；竖直面参与镜像反射（会形成自我提亮回路）；线性空间量化；
`gl.finish()` 作为帧时同步手段（ANGLE 下是空操作）。
尚不确定：10 fps 上下的帧率是否能接受；`city.bin` 13 MB 不压缩是否合适；水面统一镜面高度的 3 m 视差。

迁回 Unity：先迁移判断而不是强度数字——① 城市视角的描线不该每边等亮，
亮度应随背后的光与朝向变化；② 分区反照率在城市尺度上偏亮，与"建筑是黑体块"相反；
③ 灯光的垂直衰减是零成本高收益；④ 窗光的稀疏度与提亮倍数值得单独调一轮。
近景地点的光比要另算一版，不能直接套用。

验证结果：`/heishui.html` 实际渲染并截图（七机位 × 四阶段），联络表与逐层亮度增量在
`captures/heishui-2026-10-04/`；帧时用同步 `readPixels` 实测（`npm run perf:heishui`）；
独立 Vite 构建通过；浏览器控制台无 error；实验室主页入口、返回链接、桥头与住所入口均实际点击验证。
未验证：Unity 接入、手机性能、真实窗口交互帧率（无头 Chrome 合成路径要回读画布，读数偏高）。

## 2026-10-04 · 桥头与周边街区（尺度实验）

问题：相同桥头画风在世界远景、中景和地点近景能否保持一致？
固定：原桥头主体，共用明暗映射，曝光 1.25，确定性几何。桥头构建函数增加河岸长度、地面范围和背景剪影选项，默认行为保留。
变量：河道与街区布局、建筑高度/屋顶节奏、地标层级、阴影覆盖与远近线条密度。

四镜头观察：
- 世界远景：河道与跨河亮面连接两岸，钟楼/阶梯办公楼形成焦点；关闭简化后细窗线明显增多。
- 街区中景：桥头拱廊、路灯亮区可读，周边屋顶仍偏重复。
- 桥头近景：拱桥、圆顶与钟楼仍清楚；扩展建筑成为前景遮挡和后景街墙，而不是全部描亮。
- 对岸回望：阶梯办公楼与仓库有不同的轮廓，长阴影能建立方向；远处地面留白偏大。

保留：共用明暗映射，连续河道，少数地标亮面，按线条屏幕尺寸简化。
尚不确定：街屋重复程度、道路规则程度、线条硬阈值跳变。用户尚未审图，不制定全游戏规范。
迁移：先以真实城市地点布局重做建筑分组，再将轮廓层级与屏幕尺寸判断移入 Unity；本轮未执行。

验证：街区与独立桥头 Vite 构建成功（有 bundle 超过 500 kB 的体积提示）；四个固定机位已在浏览器查看并保存截图，远景完整线条/简化线条与受光模式已切换对照，机位链接导航已实际操作；街区与独立桥头控制台未发现 error，独立桥头画面回归检查正常。未验证 Unity 接入或移动端性能。

## 2026-10-04 · 逆光 BACKLIGHT：发光地平线的价值结构

问题：城市视角的黑色电影情绪，能否只靠「发光地平线的剪影价值结构 + 真实 shadow map 低角度长影 +
一束仰射的主角塔」成立（不描线、不 raymarch、不反射 RT）？

固定条件：入口 `backlight.html` 与 `src/backlight/` 独立源码，seed 20261004，
CityBox 冻结快照 `public/backlight/city.{json,bin}`（导出 stats：外壳保留 563/剔 294、填充楼 1274、
屋顶 877、树 119、窗 3430、主场地清空 1），主角塔 118 m（填充楼最高 81.5 m、p99 25.6 m），
五个固定机位与四个阶段（体块/空气/灯/成片）；参数只在 `config.js`，阶段只改 uniform。

变量：雾密度与雾色方向项、天空热点收束、实例反照率（instanceColor）、光锥与探照灯强度、
水面波幅与反射、阴影 bias/normalBias、黑位与逐机位曝光、04 机位位置。

五机位观察（`captures/backlight/2026-10-04/`，联络表 + 分阶段亮度统计）：
- 01 隔河对望：shape 阶段黑剪影贴暖带即成立；水面修复后是干净暖反射带；light/final 中景仍偏奶（bright>20% 54%）。
- 02 主角塔：仰射立面 + god rays 是唯一焦点，壁柱/收分/冠部可读；光锥从"白墙"降到"柱"。
- 03 高位斜俯：雾色方向项修复前整张被冲成暖褐纸，修复后回到暗城 + 路网；成片 77.9% 像素低于 2%。
- 04 干道纵深：原机位半屏被前景板楼吃掉，重定为正南 (-110,14,-360)——灯珠导视、河与探照灯在左、塔居中。
- 05 远景剪影：118 m 塔与 81.5 m 填充楼比例成立；曝光 1.05→0.92 后 bright>20% 由 86% 降到 79%。

保留：价值结构先于一切（零盏灯时剪影已成立）；天空与雾共用 `skyBase()`；雾色按方向取
（往上看是天、往下看是地面暗霾，4 行 GLSL 是俯视机位不糊的唯一修正）；近黑反照率 + 三档硬分带；
真实低角度长影；四阶段只改 uniform 的可复现 capture；加性光柱量级（0.035 是柱、0.10 是墙）。
放弃：雾密度 0.00205/0.00095、天空宽晕 6、黑位 0.020、水面恒定微幅与 0.85 反射、光锥 0.10、
统一曝光、04 旧机位。尚不确定：中景是否仍偏奶、竖窗带是否过亮、03 成片是否太黑、真机性能（未测）。

原因：先验证情绪是否由结构给出，再谈灯；每一处参数改动都以五机位实际画面与亮度统计为判据，
不用"更酷"判断。迁回 Unity 的是判断不是代码：雾色按视角方向取、近黑反照率 + 硬分带给层级、
低角度键光与大范围阴影是"逆光"的证据、加性光柱只指向焦点；绝对数字不搬，只搬比例。

验证：`npm run build:backlight` 通过；`node tools/capture-backlight.mjs` 实跑 20 图 + 联络表 + 统计，
脚本内建 pageerror/console.error/HTTP≥400 检查未触发；本轮 6 次人工查图（含全尺寸裁切）；
导出脚本在 Blender 5.2.2 无头跑通。自由环视可钻到地下出大块硬边黑块（实测相机 y = −94.8 m），
已加每帧地面约束 `camera.y ≥ 3`（`updateCamera()`，固定机位最低 y = 14 不受影响），
修复后回归 capture 与修复前逐格一致（仅 02 光脉冲 0.001 级差异）。未验证真机帧时、屏幕观感与 Unity 接入。
