# 接续与自主研究协议

本实验应当能脱离聊天记录继续工作。用户说“继续实验”时，执行实际的实现、截图、观察和改进循环；不要停在计划或描述上。
模型可以调整自己的工具与判断方法，但必须维持下面的证据链。设计目标仍以 DESIGN.md 为准。

## 新 Session 从这里开始

1. 读仓库根 AGENTS.md、本实验 AGENTS.md、本文、DESIGN.md。
2. 读 CHECKPOINT.json，再读 RESEARCH_LOG.md 最近的结论和当前问题相关的失败记录。
3. 有本地环境时，在实验目录运行 `npm ci`、`npm run status`。状态命令不需要启动浏览器。
4. 优先处理 pendingReviews。没有待审图时，打开 acceptedBaseline 指向的 contact sheet 和四张 Final；有必要再看对应 Shape / Line / Preprint。
5. 如果源码指纹已变化，查看实际 diff，再给当前代码生成一组新的完整截图。不要把旧图解释成当前版本。
6. 把当前基线的主要问题说清楚，选一个研究问题，开始下一轮。nextQuestions 是研究候选，不是必须照顺序完成的功能清单。

`visualCodeCommit` 是已验证视觉实现的提交，不是“仓库必须永远停在这个 HEAD”。后续文档或工具提交不必让视觉基线失效。
`sourceSha256` 只覆盖 src/ 的路径和文件字节；HTML、依赖、浏览器或 capture 工具发生视觉相关变化时，即使指纹相同也应重新拍图。Git、完整 manifest 与实际 diff 一起作为证据。

## 文件各自承担什么

| 文件 | 内容 | 何时更新 |
|---|---|---|
| DESIGN.md | 艺术目标、非目标、架构、阶段与判断优先级 | 方向或长期设计发生变化 |
| AGENTS.md | 工程边界和不可跳过的接续入口 | 协作规则变化 |
| CONTINUE.md | 自主循环、审图、交接和流程改进方法 | 方法经过验证后改进 |
| CHECKPOINT.json | 当前已接受基线、待审证据、下一步问题、已知限制 | 每次接受新基线或中断工作 |
| RESEARCH_LOG.md | 问题、变量、观察、保留/放弃/不确定和迁移结论 | 每个有意义的实验完成 |
| captures/reviews/<唯一名称>/ | 图像、manifest、报告和该轮说明 | 需要长期保存的基线或关键失败 |

聊天中的 compact 可以方便导航，但不能成为项目唯一的状态来源。

## 选择可用的循环

**本地优先**：Linux / Mac 等能运行 Node 和浏览器时，使用现有 capture 工具。Playwright 默认 headless shell；完整 Chrome 在受限 Linux 下可能因进程锁 socket 失败，换配套 headless shell，不把环境故障当成美术结果。

```bash
npx playwright install chromium
npm run capture -- --shot 03-alley-mouth --mode final --out captures/trial-unique-name
npm run capture -- --out captures/candidate-unique-name
```

第一条用于快速验证局部假设；第二条输出四镜头、四模式的 16 张图。先确认新的候选目录名，不覆盖 acceptedBaseline。
`captures/latest` 是缓存，可以覆盖；`captures/reviews` 是持久证据，重要结果必须随代码提交到 Git。

**没有本地渲染环境**：使用 `.github/workflows/noir-engraving-captures.yml` 的 Actions，等待任务完成、下载 artifact，再实际打开图片。记录对应 commit、run、artifact 和审阅状态。不要只看 Actions success 就判断艺术改进成功。

本地与 CI 都无法提供新图片时，保留已验证基线，记录阻塞和未验证假设；不能把未经观察的修改写成已成立的结论。
不要依赖某个特定聊天插件、桌面工具、机器路径或会话缓存才能接续。

## 一轮研究的完整闭环

1. **问题**：从图像提出一个主要问题，例如“远端目标被两侧白墙抢走”，而不是“加一个 shader”。
2. **假设**：写明预期结果与什么观察会证伪它。固定镜头、seed 和无关参数。
3. **实现**：仅改变回答该问题所需的变量；视觉参数、场景、灯光、空气、Print 各留在自己的模块。
4. **截图**：局部试拍加速搜索；候选成立后检查全部四镜头和分层图。
5. **观察**：必须打开图片。先看第一阅读点和主体层级，再查黑面积、结构、光边界、空气和媒介统一性。
6. **决定**：保留 / 放弃 / 尚不确定。编译成功、指标更漂亮、效果更显眼都不能单独作为保留依据。
7. **记录**：保存关键证据，写 RESEARCH_LOG；只在实际审阅后把 checkpoint 的 visuallyReviewed 设为 true。
8. **收敛**：当前问题解决且四镜头没有实质回退时，建立新基线，再选下一问题。若连续改动只是在互换缺点，恢复基线，换假设。

可以主动改进实验循环，但不要为了持续工作不断堆效果。当一项研究已稳定，应该形成结论，而不是不停微调同一个参数。

## 固定审图问题

所有镜头都问：第一眼看哪里？黑暗是否承担遮挡与构图？主体靠 silhouette、亮面和少量线是否成立？普通建筑有没有重新争抢权重？

| 镜头 | 专项问题 |
|---|---|
| 01 Theater Street | 红牌、入口、亮侧面是否共同指向剧院？普通街屋能否退后？ |
| 02 Warehouse Fog | 工业轮廓、工作区和纵深是否可读？叙事灯是否提亮无关屋顶或道路？ |
| 03 Alley Mouth | 是否有黑前景 / 冷中景 / 暖远端？有无明显圆形光斑？顶棚和平台是否在真实切光？ |
| 04 City Compression | 前景黑块是否形成框景？地标是否被裁断或变成空白线框？城市层级是否被均匀照明破坏？ |

Shape 仍含基本与叙事灯光，不是“关闭所有光源”。Line 恢复结构线；Preprint 恢复空气和 Bloom；Final 加上 Print。
数字用于定位差异：black<2%、bright>20%、层影响、耗时和必要的像素比较。不要把某个黑面积百分比写成适用于所有镜头的审美门槛。
更换机位会改变统计的含义，不能把构图变化全部归因于渲染改进。

## 流程如何自我改进

每轮同时问：有没有等待、重复安装、无法归因的变量、丢失的图、漏报错误或难以接续的判断？

- 找到实际瓶颈，测量时间或复现错误，再改工具。
- 保留完整回归与审图；快速局部模式只降低搜索成本，不取代验收。
- 错误要带来源；资源失败、JS 异常、shader console error 不能悄悄变成空白成功图。
- 不加入依赖外部会话才能运行的流程，不维护两套来源不同的状态。
- 若改进确实减少耗时或避免漏报，记录条件、测量与局限，再修订本文。
- 数字分析、图像拼版和任务选择可以自动化，艺术结论仍需要实际读图，并说明为什么。

## 每次结束或中断前

保存四类信息到仓库：已接受版本与证据；已观察的失败与原因；未审阅的候选和准确位置；下一项可检验的问题。
截图任务刚完成却还没打开时，把它写进 pendingReviews，下一会话先审图，不能直接继续改代码。
更新 checkpoint 时确认 manifest 指纹、review 路径、四镜头文件和审阅状态一致，再运行 `npm run status`。
已知失败（包括无效 Light Layers、全城后巷灯、近墙白弧）必须继续保留，避免未来重新踩坑。
不把尚未验证的假设改写成 DESIGN 的既定原则。
