# 巷战镜头穿墙检查

2026-10-29。敌人出手触发三台「巷战还击」Static 镜头，原脚本只核终点在巷内，未核途中路线。

正式工具：[tools/camera-review](../../tools/camera-review/README.md)。Unity 和命令行直接编译同一个 FocusTravelMath.cs，焦点解析、默认路径选择、位置与构图采样共用计算；Blender 不再手抄曲线。

- shared-before/：添加空间约束前，8 台作者机位的 56 个有向组合有 29 条所选路线发生几何穿越。总览到三个还击镜头都被默认策略回退为 AuthoredArc，随后绕出巷道、穿过侧墙。
- focus-candidate/：历史候选，离线输入使用人物交手位置作为兴趣点，仍然穿墙，因此未给正式运行时增加 Focus 配置。此快照使用实验时的临时输入解析，不是最终 CLI 输入契约。
- final/：正式场景加入一个 CameraTravelBounds_巷子里在打人 三维通行盒，覆盖巷内与总览可用的巷口空间。保留 27 条运动，29 条越界路线复用已有溶解。保留的运动未检出中心线或近裁剪面穿插。routes.json 中 Crossfade=true 的曲线被拒绝，游戏不执行这条物理运动。
- unity-import/：首次整城导入尝试，处理无关动画时超过 300 秒，未通过。
- unity-import-minimal/：缩小到 City 语义模型后的最终导入核对，以 result.json 成功输出为准；不进 Play Mode。

重复检查使用工具 README 中的 Blender 命令；一次共享计算检查约数秒。整城构建发布明显更慢，不在日常循环中运行。

证据边界：这是作者机位组合，不是玩家现场录制；未覆盖飞行中拖拽偏移、状态显隐、Portal 和实际攻击/溶解交互。空间保护在发起过渡时进行。有限采样不证明完整连续体积安全；未自动判断人物遮挡和画面节奏。源模型和共享计算 SHA256 记录在 final/report.json。

check.py、report.json、blender.log 是最初可行性实验：仅查 14 件结构墙、手工重建两条曲线，不含默认回退选择，不作为最终运行时路线证据。正式工具已取代它。

最终校准：通过 unity-import-minimal/result.json 对照实际导入，修正离线坐标的 Z 符号和 FOV 取值。8 台相机对齐后的最大位置误差约 0.0000024m、最大旋转误差约 0.000018°、FOV 误差小于 0.000001°。Unity 与共享 LookRotation 检查误差为 0°。

baseline-final/ 使用校准后的输入显式忽略通行盒重放基线：56 条路线中 29 条穿墙。final/ 使用通行盒：29 条溶解、27 条保留运动，保留运动未检出中心线或近裁剪面穿插。此前 shared-after/ 的 26/30 统计属于校准前记录，以 final/ 为准。

## 迭代成本与后续默认流程

本次日志创建至最后写入的近似耗时：整城构建发布 438.63 秒；首次整城 Unity 导入 299.48 秒后超时；最小 City 导入核对 26.03 秒。共享 C# 与 Blender 检查报告记录为 1.17–1.33 秒（不含 Blender 启动/载入）。这些是一次样本和阶段级证据，不是完整性能剖析。

普通机位/通行盒/独立 Stage 内容修改不重复启动 Unity。只有新导入契约、换算/绑定实现改变、Unity 专有渲染改变、实际两端不一致或用户明确要求，才做对应最小核对。沿用现有管线的发布检查仍执行。

交付流程已消除审阅后重复构建：源未再改变时直接发布既有构建。发布器对相同内容保留文件与时间戳，避免无效重导入。构建器增加阶段及逐 FBX 导出计时，下次正常构建自动记录，不为采集性能再跑全城。

当前大瓶颈是整城构建/导出及无关动画导入。增量导出受影响 Prefab 是后续优化候选，尚未实现；分阶段计时可用于选择最值得优化的位置。UI 标签避让等纯计算也适合下次修改时提取共享 C#；实际 GPU 绘制、Unity 导入后的动画插值不能用纯计算冒充。
