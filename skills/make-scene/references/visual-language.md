# 场景视觉语言

目标是让玩家在游戏机位下读出地点身份、关键对象和空间关系。几何、表面、线、光与雾共同承担表达；不要求每个场景用齐所有手段，也不以晚宴的金色与抛光质感作为通用模板。

## 开始前读取什么

以下路径以项目根目录为基准：

- `docs/城市视觉基准.md`：共同阅读层级及世界／地点作用域。它包含连续校准记录，后面的更新可能覆盖早期说法；当前值查正式资产，不抄旧校准数字。
- `city-box/pipeline/world_style.json`、`world_style.py`：作者可用的表面、描线和光色角色，以及地点环境声明。
- `city-box/pipeline/outline.py`：描线参数、组合与生成限制；`UnityClient/Assets/Resources/City/WorldPalette.asset` 及其引用的共享 `.mat` 是正式 Unity 外观的权威。Blender 的 RGB、粗糙度与 emission 只是自身预览的实现，不反推或覆盖 Unity 参数。
- 要接入或出正式图时读 `skills/create-3d-assets/references/runtime-contract.md` 的“世界视觉基准”和 `tools/citybox-unity-preview/README.md`。若本地存在 `city-box/docs/视觉参数.md`，读取其作者选项和组合约束；缺失时查上述现行代码，不虚构文档或参数。

按需看正式晚宴、码头、码头居民区与《别给他们想要的》的源 Prefab 和审核图：分别参考材质与配光组合、前后层次、密集环境退后和冲突空间。不要把某一场的选择套到所有地点；生成脚本与 `.blend` 声明可能不同，重跑脚本前确认它能保留当前视觉声明。

`docs/TODO.md` 与 `docs/场景视觉并行探索.md` 说明尚未补齐的场景质感；它们不是已完成效果的证据。暂缓的自由探索候选没有被正式采纳，不作为风格范本，也不将其盲式探索流程用于默认的新场景制作。

## 设计方法：先分职责，再组合

读剧情、动作与锚点，写清玩家的注意力顺序：第一眼的主体、需要辨认的通路或分区、帮助定位的结构、退后的背景。把方案简记在场景 `review/<名>/prompts.md`，指出哪些构件承担这些职责、使用哪些现有角色、希望形成怎样的明暗／冷暖／反光关系。不规定每场固定几层或必须加雾。

| 手段 | 设计判断与现有入口 |
|---|---|
| 表面 | 用对象 `surface` 分配角色。主体、地面、抛光地面、象牙饰面、金色金属、暗金饰面、金色镶边及冷／暖白灯饰等由 `world_style.json` 定义。先按构件职责选择，再看受光后的明度与反光；不要把所有对象保留默认“主体”，也不要全铺亮饰面。发光灯饰的表面不等于真正的照明光源。 |
| 描线方式 | `hard_edges` 读硬表面结构；`hull` 适合人形与圆滑物件的外轮廓；`camera_silhouette` 适合固定机位下不宜描碎面的少数件；`none` 让表面／光影承担形体。`proxy` 是世界轮廓来源，不是弱化近景线的选项。 |
| 线宽与碎边 | 顶层集合的 `line_px`、`min_edge_px`、`angle_deg`、`min_edges` 按地点相机控制近景描线重量和细节保留。先减少无意义的碎边、调整主次，再调宽度。当前入口不是每对象任意 `line_px`；需要对象差异时使用现有策略和亮暗，不假设后端已支持新的逐件线宽。 |
| 线的亮暗与色彩 | 对象 `tone=bright|dim` 组织主次，不决定显隐。当前 `DIM_LINE_SCALE=1.0`，dim 靠暗色退后，不能声称它自动变细；共享 Mesh、人形壳和会动部件也须检查具体分支是否采用 tone。`line_palette` 可选金色结构线、象牙装饰线、金色镶边线等现有装饰角色，检查生成路径与 Unity 映射是否支持；不要假设它与 dim 或所有描线方式任意叠加。通用主线仍为略冷的白色，金色须有构件职责。 |
| 配光 | 选择已有 `light_palette` 冷白、冷边、暖白、琥珀，组织主光、补光、轮廓分离或可见灯具对应的照明。地点灯声明 `visual_profile`、`lighting_mode`，位置、方向和能量来自源资产；模式、强度与尺寸查实际发布链。不靠提高整体曝光修补一个局部暗角，不用均匀补光照平所有体块。 |
| 环境与雾 | 地点声明 `visual_world`、`visual_fog`、`visual_fog_start/end` 等，按当前导出和消费代码设置。环境补光保持暗部可读，局部距离雾可使远处退后，但不能遮掉交互落点或把前后都洗成灰。世界高度雾与地点距离雾的作用域不同；统一调色、曝光、颗粒、暗角及近景 Bloom 倍率查 WorldPalette 的当前实现。 |

例如：关键家具可以用清楚的轮廓和局部受光被看见，围合墙面用较暗表面与结构线保持空间，少量灯饰给冷暖方向，远处是否用雾取决于距离和情景。精致感来自这些关系，不来自线、金色、反光、灯或雾的数量。

灰盒先确认空间，再在占位体上做层次试配；精细道具替换后重新看轮廓、反光与遮挡。灯的位置应与场景可理解的照明方向相符；材质承担形体，描线补足阅读，不让每条墙缝、窗框、椅腿都与关键轮廓争抢。

## 局部与共享边界

默认组合现有角色，只改本场景的几何、对象角色、集合描线参数及地点配光／雾声明。共享 `.mat`、WorldPalette、URP、Shader 和世界配光默认只读；其作用范围按实际引用判断，不能因只预览一个场景就当作局部参数。不要复制共享材质来绕过共同基准。

确有表达缺口时，另提出共享基准建议，说明局部方案为何不足、拟改角色或参数和其他场景影响，并提供隔离对照；审核前不改正式共享资源。不为场景精修新增呈现功能。

## 审核与交付

Agent 先从游戏相机自审，不能只交一张漂亮概念图：

- **注意力与空间**：不读说明也能找到主体和主要分区；布局仍支持脚本里的行动，画面没有靠招牌、光效补救错误空间。
- **线与表面**：关键轮廓清楚，背景退后，密集碎线不糊成白团；暗部和反光处仍读得出形体，没有所有线一样抢眼或主体无意间失去轮廓。
- **光与雾**：主次和冷暖有理由，保留暗面；雾不吞掉人物、动作落点和通路，高光与 Bloom 不把装饰推成主角。需要烘焙的场景检查光照资源是否随几何更新，尤其晚宴的哈希契约。
- **机位与 UI**：根机位及相关补充机位成立；Pan 中心与四角、Orbit 的实际可达视角仍能读到关键对象。卡片、连线与对白覆盖下的阅读须在正式游戏检查，单体预览没有这些 UI。
- **共同语言**：与代表地点比较主次和材质职责，不强求同样亮度或装饰；外壳或世界轮廓有变化时也检查世界视角，嵌套场景检查所属顶层地点的显隐与配光。

用 Blender clay 图审空间，用 Blender `--game` 图审构建描线与初步组合，最终用正式共享资源的 Unity 画面审质感。`--game` 仍是 Blender，不保证 Unity 材质、后处理或烘焙光照相同。正式资产发布后可按预览 README 运行 `python3 tools/citybox-unity-preview/preview.py --scene <名> --verify-play`；它读取已发布资产，不消费未发布的候选 `.blend`。未授权发布时交候选图并说明尚未取得正式 Unity 证据，不用临时材质映射冒充正式效果。

交付保留同机位对照（新场景可用灰盒对照最终版本）、所用表面／描线／光源角色、局部参数和取舍理由；标明每张图的渲染来源。报告实际检查范围，区分构建、固定机位 Editor/Play 一致性与真实交互；未检查的 UI、拖动、动画或手机表现明确写未检查。
