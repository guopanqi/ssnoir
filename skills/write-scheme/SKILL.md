# 写 SSNoir 的 Scheme 内容

把 [engine.scm](../../UnityClient/Assets/Resources/Content/scripts/engine.scm) 当作 DSL 的唯一事实来源。使用陌生构造、签名不确定、
遇到接口报错或准备扩展 DSL 时，用搜索定位并读取相关定义与调用点；**不要为每次内容修改通读整个文件**。
参数个数、哪些构造必须传 `outcome`、风险等级、势力名、能力范围和节点形状，应由
`engine.scm` / `NodeConverter.cs` / `NativeFunctions.cs` 的 `error` / `throw` 强制，而不是靠本文复述。
**你已经会 Scheme，本文不教语法。**

写节点优先用包装函数（`container` / `action` / `instant-action` / `observe-action` /
`roll-action` / `note-node` / `clock-node` / `工作`），让构造器表达节点的用途。现有包装函数无法表达所需的 `subtitle`、`tags`、
`clocks` 或 `disabled` 组合时，可以使用裸 `node`；若同一种裸结构反复出现，优先补齐 DSL 接口，
不要继续增加一次性包装函数。

**禁止渲染空 Container。** Container 只表达确实存在的层级；没有子节点时必须省略。仅展示说明或
Clock 的叶节点用 `note-node`（见下文「标注不是卡」），不要用 `observe-action` 冒充纯展示。
可选子节点为空时，不要留下只有标题的 `container` / `:children '()` 占位。

### Node Id 是身份，Node Name 是显示文字，Anchor Name 默认取 Id

Scheme 的 `node` 第一个参数是稳定的 `Id`；`:name` 是玩家看到的显示名称。对应到 `GameNode`，
`Id` 在整棵渲染树内必须唯一，`Name` 可以重复。不要把显示文案当身份，也不要另建路径来消歧。

- 同一渲染树中的每个节点 `Id` 必须全局唯一，不只要求同级唯一；重复 ID 就让引擎直接中断。
- `Name` 只负责显示，可以在多个节点上重复。`:name` 省略时显示名称沿用第一个参数的 `Id`。
- 遇到两个语义相同的动作，用稳定且唯一的第一个参数区分身份，并用 `:name` 写自然、清楚的玩家可见文字。
- Unity 默认用 `Id` 查找同名 `NodeAnchor`（`AnchorName` 默认等于 `Id`）。只有同一个节点会出现在多个空间位置，或多个节点应共用一个空间落点时，才用 `:anchor` 显式覆盖锚点名。
- 不写 `:anchor` 时，Unity 先按默认锚点名（`Id`）查找 Anchor，找不到就进入网格布局；这是普通动作没有空间落点时的正常路径。
- 显式写了 `:anchor` 就表示作者要求空间投影；Unity 找不到该 Anchor 会立即中断。Anchor 名在整个
  Unity 场景中必须唯一，例如同一人物移动时使用 `夜莺@酒馆` 与 `夜莺@剧院`。
- `:anchor` 的值可以是运行时算出的字符串。多个互斥节点可以共用一个空间落点，例如几个动态标题都
  声明 `:anchor "码头@邮务踩点"`。
- **要知道现有哪些 Anchor 可用，列模型，不要翻 `Main.unity`。** 锚点是 Blender 那头的
  `Anchor_<节点名>` 空节点，导入时由 `UnityClient/Assets/Editor/Pipeline/SSNoirModelImporter.cs`
  挂上 `NodeAnchor`；场景文件里只留了几个特例，照它判断会得出「这个锚点不存在」的错误结论。
  命名契约见 [create-3d-assets/references/asset-contract.md](../create-3d-assets/references/asset-contract.md)。
  列出全部可用锚点：

  ```bash
  python3 skills/write-scheme/scripts/list-anchors.py
  ```

场内非队员的 Bubble 台词必须显式用 `:at "已有Anchor"` 指定发声位置；人物身份不能代替空间落点。
尼尔与队员可以自动定位，旁白无需锚点。具体边界见 [表现接口](references/表现.md#说话人怎么解析)。

### 普通配角的身份与肖像

普通配角可在所属故事文件就近声明 `(speaker "稳定身份" :name "显示名" :appearance '成年男性)`，
再传给 `line`。`:appearance` 省略时使用通用剪影；有专属肖像始终优先，不按职业猜性别年龄。
类型池不登记逐个人名。完整用法与限制见 [人物声明](references/表现.md#普通配角在内容附近声明不维护中央人名册)。

### 必须在休息前处理的内容由节点自己声明

```scheme
(node "醉客互相叫骂"
  :required-before-rest "先平息两桌争吵"
  :resolve ...)
```

值为非空提示字符串；条件不成立时可传 `#f`，等同于不声明。引擎扫描整棵世界树，自动取得节点身份和所属地点，用于休息禁用、信标与换日检查。也可声明在有入场事件的地点或有可用动作的容器上；不能放在交锋、纯标注、不可进入的地点之外或禁用的处理路径上。

节点出现即必须处理，剧情状态改变后节点消失或不再声明，即解除；读档只恢复剧情事实，不登记、释放或同步另一份阻塞状态。不要再写 `rest-block!` / `rest-release!` / `sync-blockers!`。

必须节点的存在及其声明只依赖剧情事实，不能反过来依赖 `rest-blocked?`，否则形成循环声明。`rest-blocked?` / `rest-block-reasons` 只读引擎投影，主要供睡觉卡呈现使用。世界换日的 C# 和 Scheme 入口均由引擎检查，交锋结束回合不受世界节点影响。作者仍须保证处理事件所需资源可获得；字段本身不会发放骰子或免除成本。

### 约定必须由剧情与可执行节点共同落实

人物发出邀请不等于尼尔已经答应。可选邀请提供接受与拒绝；接受后，到约定当天用现有
`:required-before-rest` 声明必须赴约。主线替玩家作出的承诺必须在 Dialogue / 演出中明确说出，
同样落实必须处理，不能在到期规则中默默写成错过。未来约定提前进入「手头的事」，不提前阻止休息。

必须赴约不等于必须投入额外资源帮助对方。到场听完等合理处理方式可以完成约定；不能因行动骰
耗尽把玩家锁死。有限期委托接受后可以因到期失败，不因“已经答应”强制阻止换日，也不自动添加
主动退出按钮。是否允许撤回由具体内容决定；经理演出服委托只有交付或逾期失败。
声明只读真实剧情状态，完成对应事件后解除。

### 手头的事记录已知片段，而不只是待执行动作

人物片段还有后续生活变化、约定或已知待续时，事项保持“进行中”，即使当前无需玩家行动。
完成一个 Clock 或交付物不等于整个片段结束；例如安排好代班后仍记下露西入学、暂时离店和返店近况，
直到现有片段的收尾发生再标为了结。正文随尼尔实际得知的事情更新，不提前透露幕后事件。
未认识、未听说的片段不显示。不要用“今天没有按钮”判断片段是否结束。

物品交付使用 `req-item` 表达资源要求；缺少物品由资源槽限制执行，不要再因为背包数量不足设置
`:disabled`。节点保持可用，玩家能看见并准备交付目标。

### 动作按钮可以指定动词

可交互动作可用 `:button-text "委派"` 指定按钮文字，也可根据状态计算。未指定时沿用
客户端默认的执行 / 查看文字；禁用、待命与执行中状态仍由客户端明确呈现。
只改变按钮文案，不改变节点名称或动作效果；容器与 note-node 不允许声明。

### 统一行动风险（2026-10）

- 判定概率由骰子、技能、修正和 `FateStrip` 决定，`风险等级` 不修改概率。
- 对 Roll 节点声明 `:risk '稳妥 / '冒险 / '危险`。稳妥：坏结果通常无进展或只有已告知的轻微代价；冒险：坏结果触发明显额外代价；危险：中结果也可能造成代价、坏结果更加严重。
- `:risk-target (list 'clock "夜莺的恐惧")` 表示主要负面影响；`:progress-target (list 'clock "回到住处")` 表示正向进展。个人状态用 `(list 'composure "player")` / `(list 'injury "player")`；物品用 `(list 'item "金钱")`。
- `:risk-target` / `:progress-target` 可用于判定或确定性行动，不依赖 `:risk`；花钱推进Clock也应声明进展目标。`:risk`仍只用于Roll。
- 目标是**预告与高亮**，不会自动结算；作者仍须在三个 outcome 中唯一落实实际效果。不能出现 UI 和结算互相矛盾的声明。
- 地点/交锋的自动回合效果需在可见注释或场景规则明示；不得隐藏成某张动作卡失败时的额外代价。
- 有 `:risk` 的卡不得再写“低风险”“高风险”风险标签；“工作”“交锋”“非法”等类别标签与风险分离。
- `工作` 的风险参数统一改为 `'稳妥/'冒险/'危险`；旧 `'低/'高` 只作为历史内容兼容输入。
- `clock` 目标按 `GameClock.Label` 验证，必须存在、无歧义；用错目标视为内容错误，不静默忽略。

### 标注不是卡

`note-node` / `(note 标题 正文 [钟])` 产出的是**标注**：漂在场景里的一段只读说明。它没有卡框、
没有底、没有影子，**永远不可点**——不能翻面、不能执行、不能导航进去。三个字段都可选，至少要有
一项非空。它唯一的反馈是自己变了：值一动就亮一下再落回。

和 `observe` 的分界是一句话：**标注是「站在这儿就看得见的」，`observe` 是「你去查了才知道的」。**
环境叙事、常驻状态用标注；要玩家花代价才揭开的信息才用 `observe-action`。
人物标注只描述眼前可见的在场、缺席、伤势或活动；不显示隐藏的帮忙条件、每日救场次数、
冷静恢复收益等规则。人物的实际帮助由事件和表现体现，不把人物标注写成机制说明。

**`observe-action` 只在「这条信息值得玩家专门去查」时才成立。**两类最常写错的，一律用标注：

- **「这个场景现在是什么样」**——交锋里的「此刻的场面」、地点的环境近况、局势播报。
  做成 observe 等于要玩家花一次点击去看本来就该常驻的东西，还占掉一格可交互版面。
- **纯氛围**——只写环境、不改变状态、也不给玩家任何可据以决策的信息的卡。
  除非用户明确要求，不要自主添加；它验证不了任何玩法，只会把真正要读的卡挤下去一格。

摆在哪由锚点决定，和动作卡同一套规则：解析得到锚点就浮在那一处旁边、一根线指过去；没有锚点就
升到画面上方的场景标注带，说的是这一整场。**标注不进网格。**

`clock-node` / `clock-nodes` 是标注的一种——带读数的那种：第一个参数是标注节点的 `Id`，显示为钟标签，正文取钟的 note；钟的进度仍由钟对象自身保存，不在节点上重复保存。

Clock 是表现世界中某件事情进展的载体。标题写正在争取或改变的事情，正文说明人物处境与进展的意义；
不要把正文写成“判定推进0／1／2格、每格折算多少钱”的公式。具体投入、判定与价格由相应行动卡说明。

### 带配音对白必须同步资产

`line` 的第三个参数是稳定的配音 ID。只要修改或删除带这个参数的对白，就必须同步检查
`角色库/配音/清单/*.json`、`角色库/配音/候选/` 和 `UnityClient/Assets/Resources/Voices/`：

- 修改台词时保留配音 ID，更新清单中的 `text` 使其逐字匹配新的 `line`，并重新生成、验收对应配音；旧音频不能继续作为新台词的成品。
- 删除台词时删除对应清单项、候选 `.wav`、Unity 已接入的 `.wav` 及其 `.meta`；仍被其他对白使用的目录和资产保留。
- 只有用户明确要求保留旧配音时，才可以跳过同步；新增第三参数时也要补齐对应清单和配音资产。

用配音 ID 搜索全仓库确认没有遗漏。历史文档中的旧台词不属于运行时资产，不因内容修改而清理。

### 节点信息：标题、描述、Tag、Clock

按节点职责选择需要的信息，不要求每张卡填满所有字段。标题表达「是什么」，描述表达具体情况、行动或后果；
Tag 表达性质与规则，Clock 表达数值与进度。展示形式与规则数据分开：

- 普通 Tag 来自 `:tags`；「必须处理」是带特殊关注样式的 Tag，其阻止休息的规则来自
  `:required-before-rest`。不能只写一个同名字符串 Tag 来代替真实规则。
- Clock 可以保留完整进度图形，也可以选择 **以 Tag 形式显示**。后者仍是 Clock，保留读数、
  变化反馈与结算语义；不是独立的「小 Clock」类型，也不是把数值拼成普通标签字符串。
- 普通 Tag、必须处理 Tag、以 Tag 形式显示的 Clock 共用节点的同一 Tag 区，统一排列与换行。
  必须处理的特殊强调用于引导玩家关注，不另建一种节点展示元素。

### 制作记号不能进入玩家文案

`D11`、`C1`、`N4`等日期／节点编号只供代码与设计文档使用，不写进对白、事项、Clock备注、节点名称或副标题。
玩家需要期限时用当前日期推导“今天／明天／后天／几天后”，或写故事中已经明确的约定。
审阅时检查运行中的事项与条件分支，不能只检索 `line` 台词；颜色、资源ID、存档键与报错信息不属于玩家叙事文案。

### 玩家可见文字要按手机的尺寸写

界面在手机上会自动放大（一屏能放的东西变少、每样东西变大），所以**手机是最紧的那块画布，
按它写就到处都成立**。下面是各处的最大长度；标点同样占一个字符。

| 字段 | 最大长度 |
|---|---|
| 地点名（有 `:anchor` 的容器） | 8 字以内 |
| 动作 / 一般节点标题 | 8 字以内 |
| `:subtitle` | 30 字以内 |
| 便签（风险 / 修正标签，每张卡最多一枚） | 5 字以内 |
| `result-supplement!` | 20 字以内 |
| 边缘信标的理由 | 8 字以内 |

**一张卡上最多让玩家读三样东西。** 手机上一张动作卡只有 280×210 左右，而卡能画的元素有
十种：时钟徽章、能力栏、标题、副标题、边缘便签、技能药丸、骰位、展签、执行按钮、命运条。
全用上就是一张谁也不看的密度图。取舍顺序：骰位和执行按钮必须在（那是交互），标题必须在
（那是身份），剩下的每加一样都要问"少了它玩家会做错决定吗"。

具体两条：`clock-node` 一条标注只放一根钟；它不渲染节点的名称或副标题，只展示这根钟自身的
标签、进度和备注。需要同时持续显示多根钟时用 `clock-nodes`，它会各自立成一条标注。
**同一张可交互卡上不要出现第三处数字**——难度修正便签、能力栏等级、骰位面值已经是三处，
玩家得在 280px 宽里同时解析。标注不占这个额度：它不是卡，也不参与交互。

两条更要紧的写法约束：

- **副标题写"是什么"，不写"为什么不能做"以外的背景。** 手机上没有悬停，一切靠悬停才看得见的
  信息等于不存在；反过来，卡上写的每一句都是常驻占地的，不能当注释用。
- **别把关键信息只放在一处长文本里。** 一屏能同时看到的卡从桌面的五六张掉到两三张，玩家是
  滚动着读的；重要的东西该走 `spotlight!` / `play-dialogue!`，不是塞进第三行副标题。

在节点卡上，用 `(clock-priority (某某钟 'render-data) 'secondary)` 让 Clock 以 Tag 形式显示，带小图形和「名称 当前/上限」；独立标注仍用原徽章。默认 `primary` 显示完整进度图形。这只改变展示，不改变 Clock 的结算或存档。Clock Tag 不展示备注，必要的期限后果仍须在行动前可见。

时钟样式与好坏方向分开：`gauge` / `pressure` / `countdown` / `readout` 不决定颜色。
使用 `:beneficial-direction 'increase`（增加有利、绿色填充）、`'decrease`（减少有利、红色填充）或 `'neutral`（中性、金色填充，默认）。同一声明同时决定结算色：有利变化绿色，不利变化红色，中性变化中性色；数字保留真实正负。主次展示与残卡保留该属性，存档仍只记录格数。

```scheme
(make-clock "愤怒值" 6 'countdown "归零后冷静。" :beneficial-direction 'decrease)
(make-clock "前进" 8 'gauge "抵达住处。" :beneficial-direction 'increase)
```

敌人生命、愤怒、恐惧通常减少有利；目标进度、剩余耐心、交租剩余天数通常增加有利。不要按对象是否危险或是否倒计时来判断。两端皆有风险、需要适中或取决于玩家目标的数值用中性；新写时钟要明确判断方向。
手写 clock tuple 的第八项是主次，第九项是方向；`clock-priority` 保留方向。

**时钟默认用 `make-clock`**，交锋和世界模块用的是同一个对象：格数、上限、备注、进退、存档都收在
它自己的闭包里，改上限只改 `make-clock` 那一行。它的消息表写在 `engine.scm` 的定义上方，
传错名字或参数个数会报错并回列整张表，不必先读实现。

容器上的 `:clocks` 只在容器仍是一张卡时可见；点进容器后它不会跟进下一层。跨导航持续跟踪的状态应使用
`clock-node` 单独立一条标注，且根容器禁止挂 `:clocks`。`clock-node` / `note-node` 的第一个参数是节点 `Id`，只用于身份，不会显示给玩家；它在整棵渲染树内必须唯一。
`:name` 可单独指定显示名称并允许重复。

只有当**时钟表达不了这个状态**时才手写 `(list 'clock 标签 当前 上限 样式 备注)`。真实的例外有三类：

- **它渲染的是别处已有的真相**，自己不持有格数——例如把库存里的金钱画成进度条
  （`(min 目标 (item-count "金钱"))`），或由几个 flag 数出来的「五项准备」。没有格数可存，也没人推它。
- **上限会变**——房租续期会把上限一起抬高，`make-clock` 的上限是固定的。
- **格数会越界**——照料乔的进度可以跌成负数（负数＝他会死），而 `make-clock` 一律 clamp 到 0。
  拔河式的双向位置也属于这一类。

### 规则信息要在行动前可见

像桌游一样，让玩家从当前信息界面判断「还能等多久、不处理会怎样、每回合会发生什么」。
写有期限、换日消失、必须处理或持续结算的节点时，不能只把规则藏在条件代码、一次性对白、
Bubble 或过期后的通知里；相关节点存在期间，应持续展示会影响玩家选择的信息。

- **限时机会**：邀请、答复、赴约等会在换日后消失的节点，用 Countdown 显示剩余回合。
  今晚有效就显示 1/1；容器进入后看不见父卡，因此其答复子行动也要带期限，后续赴约动作同样声明。
- **按信息职责选择展示**：交锋的主要目标或核心压力用完整 Clock 图形；附带期限用
  `(clock-priority data 'secondary)` 让同一个 Clock 以 Tag 形式显示。
  普通性质用 `:tags`；必须休息前处理的事件用 `:required-before-rest`，由引擎产生特殊强调的必须处理 Tag。
  有期限不等于必须处理，不要把可以错过的机会变成休息阻塞。
- **持续规则**：每回合增减、期限结束的后果，应在相关节点的现有标签、副标题或常驻标注中明确呈现，
  必要时写出数值和结算时机；结算发生时再给对应反馈。不要为此先新增标签类型或计时系统。
- **展示与结算同源**：剩余回合从实际日期、已有 Clock 或剧情状态推导，不另存展示专用倒计时。
  审阅时对照节点出现、进入子层、选择分支、换日与读档，确认提示和真实失效条件一致。

只展示影响决策的信息；避免把同一条期限或规则同时重复写进标签、副标题和额外标注。

### 内容表现必须让玩家读懂因果

写会新增节点、改变局面或在回合结束自动结算的内容前，必读 [表现时序与落点](references/表现.md#什么时候播放决定了你能让谁说话)；写交锋持续规则时，再读 [交锋回应规则](references/交锋.md#零交锋回应规则)。这两处是时序与组织方式的权威说明，不从 Scheme 调用顺序猜客户端画面顺序。

作者负责让规则可预读、变化有原因、必要时声明导航落点；客户端负责结果阅读时间、提交边界和落点等待。持续效果不能只改数值，也不能只在首次出现时解释；使用已有标注和反馈，不另造一套图标或定时系统。

下面按内容职责展开：
- 写对白 / Bubble / Narration / 演出 → [references/表现.md](references/表现.md)，其中「Bubble 的内容边界」规定：气泡只写可错过的简短氛围与少量交谈，不承载必要说明。
- 把一段对白排成戏（姿势、距离、灯、画面；运镜目的与连续性）→ [references/舞台.md](references/舞台.md)
- 写交锋 → [references/交锋.md](references/交锋.md)

## 一、文字风格

世界是**上世纪美国、黑色电影（Chandler / 马洛）风格的港口城市**。语言是中文，但**世界不是中国**。

### 中英双语：只在启动页切换

语言只在启动页（`TitleScreen`）切换，游戏中不切，不进存档。不要为游戏中切换写逻辑。

`(tr 中文 英文)` 在渲染求值时执行：节点 lambda 每次重求值，切语言后重建渲染树即生效。
顶层 `(define x (tr ...))` 只在加载时求一次，靠标题屏 → 新游戏/读档重建解释器刷新；不要在顶层缓存玩家可见文案。

## 二、引擎背着你做的事

### 交锋入场演出的空间边界

- 城市侧发起交锋的动作负责出发前／门外的演出：在 `start-encounter` 前调用 `play-dialogue!`、`play-motion!` 等，客户端先播放这些步骤，再切入交锋空间。
- 交锋的 `on-encounter-enter` 负责初始化交锋状态及交锋空间内的开场演出。状态在加载时立即初始化，阻塞演出进入 `PostSceneBlockingSteps`，在客户端完成空间切换后播放。
- 判断依据是**当前演出属于哪个空间**，不是文字有没有“门口”“外面”。独立 Stage 可以包含街头、院子和堆场入口；这些地方的开场仍属于交锋侧。
- 不新增前后时机开关。同一段演出只保留一个内容拥有者；正式入口与演示入口可以调用共用演出函数，各自保留门槛和结算责任。
- 调试直接加载交锋没有动作报告，阻塞演出不会自动播放；要展示完整入场，使用提供演出动作的演示入口。

### 世界回合有结束与开始两侧

`define-turn-rule` 属于旧日结束：期限减少、房租结算、未处理事件到期、临时状态清理写在这里。
`define-turn-start-rule` 属于新日开始：早报、电话、来信，以及“今天开始”的事件写在这里。
引擎会先结算日终，再发放新骰与每日额度；睡眠黑幕亮起以后，才播放 turn-start 产生的
`spotlight!` / `play-dialogue!`。不要把“今早发生了什么”写进 `define-turn-rule`，否则事件语义会
落在睡前。交锋不执行 `define-turn-start-rule`；交锋回应继续使用 `define-opponent-rule`。

### 效果条目是自动生成的

动作 lambda 里对库存、伤势、冷静、关系、成长的**实际**修改，会按执行顺序写进 `ActionReport`，
前端在卡片上渲染成效果条目。

`outcome` 只是一个效果：`(outcome (lambda () ...))`。它没有标题、没有描述——结果条上的每一行
都由引擎写，内容不复述（"推进了 2 格""数了 15 金给你"这类行是噪音，直接删）。
只有从状态变化推导不出来的事实，才用 `(result-supplement! "解锁：码头账房")` **补**一行；
它是补充，不是每个结果都该有的东西。要说的话走显式表达：可错过的短促反应用 `play-bubble!`；
必要说明走 Narration，关键情节用 `spotlight!` / `play-dialogue!`。
资源槽投入算成本、不进效果条；所有条目记的是 clamp 之后的**实际**变化量。
`req-item` 对应的已投入物品由执行器统一扣除，效果中不要再次 `remove-item!` 扣同一笔费用。

### 坏结果扣冷静，不直接扣伤势

冷静是健康的**缓冲**，伤势是它被击穿之后的**溢出**——引擎已经把这条接好了：
`spend-actor-composure!` 花超的部分自动转成伤势。所以内容里写代价一律走冷静，
`injure!` 只留给**设计者明确指定的重罚**：枪伤、坠落、车撞上来这种一下就见血的事。
写一次坏判定就直接加一格伤势，等于绕过缓冲直接动身体，那条轴会被日常的失手迅速填满。

两个必须注意的：

- **动作外没有"当前行动者"**。回合规则、结算回调里 `spend-composure!` 会报错，
  要写明是谁：`(spend-actor-composure! 'player 1)`。
- **同伴的冷静归零会让他当场离场**。除非你真想让他走，代价就记在主角身上。

判定的结算以"成功 / 中性 / 失败"档位和自动效果条为主。必须让玩家看见的情节信息，
使用 Narration、`spotlight!` 或 `play-dialogue!`；`play-bubble!` 只留给可错过的简短氛围与反应。不要把重要信息藏在玩家会反复执行的
行动结果里。
