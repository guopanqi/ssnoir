# 写交锋

交锋想法与已做出来的例子见 [docs/交锋结构库.md](../../../docs/交锋结构库.md)（那是想法收集处，
不是规范）。这里只讲写脚本时的两条边界。

## 一、入场与场内转场

**交锋是一段已经开始的行动场景。** 玩家进入 encounter 后应当立刻看到可执行的交锋动作，
不能再要求点一次"开始交锋""确认身份""继续靠近"这类预备节点。

- **入场剧情由调用方播放。** 交锋前需要的对白、地点交代、"玩家采用了什么身份"，都应该在
  城市 / 故事脚本调用 `start-encounter` **之前**完成。交锋脚本把这些当作既定前提。
- **既定前提写在题面上。** 假身份、保护方案、谁在场，放进容器标题、subtitle、标签和 Clock 备注；
  不要做成必须先点击的 `observe-action`，也不要做成没有实际选择的 `instant-action`。
- **场内转折用阻塞式重对话。** 走完一段路线、敌人正式出面、局面换幕——这些真正改变题面的事件，
  用 `play-dialogue!` 交代过程，然后更新阶段状态、让下一份 render tree 接管场面。
  转场对话同样受锚定约束（见 [表现.md](表现.md)）：动作内只能让旧画面已有的角色说话；
  刚进入下一幕的角色若还没有锚点，先用"世界"叙述它的出现，或拆成下一幕里的独立对话。
- **`spotlight!` 只宣告结果。** 它适合交锋成功 / 失败 / 阶段结算这类告示卡，不承担人物对白，
  也不拿来替代换幕过程。
- **说明卡永远可选。** 删掉它之后，玩家仍须能从标题、动作和 Clock 看懂"现在要做什么、失败会怎样"。

## 二、可复发交锋的状态边界

**事件状态归生命周期最小且明确的 owner。** 地点事件由地点闭包保存，人物或故事状态由对应模块
保存；跨地点可见且会阻塞世界日程的公共调度由 `world.scm` 保存。需要持久化的 owner 必须显式
实现 `save` / `load!`，并接入 `world-save` / `world-load!`——本地 `define` 不会自动进入存档。
不要仅因多个地点会读取就把状态搬进 global，也不要把公共调度寄存在某个受影响的地点里。

**encounter 每次新建**，只读取本场需要的只读输入（场次、有没有盟友），结束时只通过
`end-encounter` 返回结果。拥有者传给 `start-encounter` 的 callback 负责统一结算、排下一场或收尾。
callback 会在重新加载 `world` 之前执行，使 owner 的状态先结算，再一次性重建正确的 render tree。
不要让 encounter 直接修改外部任务阶段。

若 encounter 必须读地点私有状态，入场前把**最小的只读值**镜像到 global；地点每次变更和 `load!`
之后都要重新同步。不要把整套地点状态复制到 global。
