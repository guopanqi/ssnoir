# SSNoir 交互与情节编排指南

本指南吸收了《Fallen London》的叙事设计经验，并用于判断一段故事怎样成为玩家可经历的过程；人物、主题和关系的质量标准另见「故事与人物」。

---

## 一、 状态与持续投入

### 1. 状态精简（State Parsimony）
在保持逻辑清晰与稳定的前提下，**使用尽可能少的独立剧情变量（Flags）和时钟（Clocks）**。多余的状态会让存档逻辑脆弱、引发难以排查的 Bug，并把玩家的界面弄得杂乱无章。

这条原则同样约束触发器、资格判断和其他条件，不只约束故事分支。优先使用已经成立的剧情事实与现有状态；不要为了模糊的“更熟悉”“更合理”另加隐性的次数、日期或 Flag 门槛。只有明确改变玩家体验且不能由已有事实推导时才增加记录；用途移除后，同时删除对应计数、写入与存档字段。

### 2. 检查重复投入中的判断是否变化

同一种判定反复执行，直到填满进度，容易只剩刷数值。检查玩家在过程中是否获得了新信息、面临不同取舍，或看见了值得期待的变化。增加一根危险 Clock 可以形成压力，但不自动产生选择；一根 Clock 也不意味着内容平庸。按这件事需要的体验决定结构，不规定状态数量下限。

### 3. 让状态说明能够被后来的人读懂
创建 `make-clock` 或定义剧情状态变量时，确保命名与备注完整、精炼、连贯。
写清状态的含义、由什么改变、会影响什么后续。作者侧说明用于理解结构，玩家侧 Clock 备注用于理解眼前处境，不把幕后变量解释直接搬进玩家界面。
- Clock 的标题写**正在争取或改变的具体事情**，正文（Note）说明**人物处境与进展的叙事意义**；绝不要把备注写成“判定推进 0/1/2 格、每格折算多少钱”的干瘪公式。

## 二、 行动颗粒度：不注水，也不要吞步

### 1. 砍掉没有实质意义的中间步骤（不注水）
连续情节之间，**绝不因为“叙事上合理”就增加点击、交谈或跨地点跑腿**。
- 如果某一步没有带来**新的选择、新的信息发现、资源取舍或必要的戏剧体验**，优先将其合并、就地衔接，或直接通过一段对白/演出带过。
- 人物固定在某地点等真实世界观限制可以保留移动；但能通过合理安排人物与物品位置消除的折返跑，绝不转嫁给玩家。

### 2. 别让单次结算跑得太远（不吞步）
一个行动节点（Action）应当只描述**一个核心动作（或两三个紧密相连的微动作）及其直接后果**。
- 如果你在一段结算里让尼尔连做了一长串事（例如：弄到伪装、潜入帮派仓库、查出谁偷了货、把人追进暗巷并扭送警局），说明你吞掉了本该由玩家体验的博弈过程。此时应当简化情节，或将其拆分为多个阶段 / 内联容器（`:display 'inline`）中的独立分支。

### 3. 动作必须是清晰的角色内行动
玩家点下按钮前，必须清楚知道尼尔具体要去干什么。即使标题和副标题带有黑色幽默或文学色彩，也必须配合受控的 **6 个常规按钮动词** 明确行动性质：

| 行动含义 | 常规按钮动词 | 设计边界说明 |
|---|---|---|
| 听取委托、询问、人物交流 | **交谈** | 普通城市委托来访优先在家门口提供「交谈」由玩家主动发起，少用进门强制自动触发 |
| 阅读、观察、留意现象 | **查看** | 仅用于**值得玩家专门花一次交互去查**的隐藏信息；一眼能看见的常驻环境一律用标注（`note-node`） |
| 投入指定物品完成交差 | **交付** | 始终用 `req-item` 表达要求；**缺少物品时不要设 `:disabled`**，让节点保持可见以便玩家准备目标 |
| 接受委托或邀请 | **接受** | 与「拒绝」配对，将决定权交给玩家 |
| 拒绝委托或邀请 | **拒绝** | 拒绝也应有合理的叙事收束 |
| 搜寻、跟踪、工作、应约等 | **执行** | 工作、搜寻、调查等实质行动默认 Roll；赴约、进入事件不因此强加判定 |

## 三、 记忆锚点与桌游式规则前置（防断片设计）

玩家是断断续续玩游戏的，有时会隔几天才上线。不要把规则和近况藏在一次性对白、气泡或过期后的通知里。

### 1. 「手头的事」是故事的记忆锚点
在《Fallen London》中，设计师用状态等级描述（QLD）帮回归的玩家找回方向；在 SSNoir 中，**「手头的事」承担同样的核心职责**：
- **记录已知片段，而不只是待执行动作**：只要人物片段还有后续生活变化、未来约定或已知待续，事项就保持“进行中”，**绝不要用“今天有没有按钮可点”来判断事项是否结束**。
- 一条事项追踪一件持续发展的事情，Clock 是它当前阶段的小节，不按每根 Clock 新建事项。普通重复工作与消费不必各建事项。
- 完成一个 Clock 或交付一件物品不等于整个故事片段结束；正文应随尼尔实际得知的事实动态更新（用尼尔的认知帮玩家回忆“我现在进展到哪了、在等什么”），但绝不提前剧透幕后事件。

### 2. 让规则在行动前可见
玩家应当仅凭当前信息界面，就能判断**「还能等多久、不处理会怎样、每回合会发生什么」**：
- **已知时间进程统一用 Clock 呈现**：需要玩家持续感知的等待开始、剩余期限与周期活动，都用 Clock 表达。底层可以保存日期或采用其他规则，显示从同一事实推导，不重复维护倒计时状态。隐藏事件的冷却与玩家未知的日程不因此公开。日期型等待使用 `日期倒计时`，无需另建一根每天扣减并单独存档的钟。
- **限时机会必须挂倒计时**：邀请、答复、赴约等换日即消失的节点，必须用 Countdown Clock 显示剩余回合（今晚有效即显示 `1/1`）。注意：点进容器后看不见父卡，因此容器内的答复子行动也必须挂上期限。
- **信息主次分级**：Scenario 的核心目标或主要压力用完整 Clock 图形（`primary`）；附带期限用 `(clock-priority data 'secondary)` 以 Tag 形式显示，不喧宾夺主。
- **持续规则常驻化**：每回合自动增减、期限结束的后果，必须在相关节点的副标题或常驻标注（`note-node`）中明确写出数值与结算时机，结算发生时再给对应反馈。

## 四、 承诺、强制事件与防死锁

强制事件（Must Events / `:required-before-rest`）与链接事件极易把玩家困死，设计时必须留出安全活门。

### 1. 区分「可选机会」与「必须处理」
- **有期限 $\neq$ 必须处理**：可以错过的限时委托或邀请，过期即按规则消失或走向失败分支，**绝不要把普通限时机会设成阻止睡觉的 `:required-before-rest`**。
- **承诺的双向落实**：人物发出邀请不等于尼尔已经答应。可选邀请必须提供「接受 / 拒绝」；只有玩家点击接受（或主线在演出对白中明确替玩家许下承诺）后，在约定当天才用 `:required-before-rest` 强制赴约。未来的约定提前写入「手头的事」，但在当天到来前不阻止休息。

### 2. 必须赴约 $\neq$ 必须消耗骰子（防止资源耗尽造成阻塞）
当一个节点声明了 `:required-before-rest`（不处理就不能睡觉换日）时，**作者必须保证玩家在行动骰耗尽、身无分文的极端情况下依然能解开这个阻塞**。
- 到场听完对方说话、当面交涉或承受训斥等**不消耗行动骰**的合理方式，同样可以完成“赴约”并解除休息阻塞；绝不能因为玩家今天没骰子帮忙，就把玩家永久卡死在当天夜晚。

### 3. 不擅自添加中途退出或认输入口
- 除非需求明确指定，**不得在 Scenario 中自行新增「暂且离开」「放弃调查」「认输」「撤退」等中途退出按钮**。
- 就算当前局面只剩高难度的保底行动，或某个机会窗口已经关闭，也按既有规则继续推进或靠引擎原生的倒下（冷静与伤势溢出）机制收束，不要画蛇添足地给玩家塞一个退场按钮。

### 4. 代价设计：先扣冷静，让 NPC 的后果可见
- **冷静是健康的缓冲**：坏结果一律先扣减冷静（`spend-actor-composure!`），引擎会自动将击穿缓冲的部分溢出为伤势。直接加伤势（`injure!`）只留给枪伤、坠落、车祸等**一下就见血的剧烈重罚**。注意同伴冷静归零会当场离场，除非有意设计，否则代价记在主角尼尔身上。
- **用状态变化让 NPC 真实可感**：当玩家在互动中看到自己的行为在 NPC 身上留下具体后果（如对方的愤怒钟下降、关系改变、处境标注更新），角色会立刻变得鲜活。但单次结算的状态变化要克制，一长串数值变动会稀释每一项的分量。
- **奖励可以攒着发**：不必每次小互动都掉零钱；把报酬扣到一段委托线的末尾一次性结算，可以强化办成一件事的感受。

###  5. 不要在自动触发的情节中直接进入危险的 Scenario
不能在玩家导航到某个地点自动触发的对白、镜头演出中直接触发 Scenario。应在合适地点提供清楚的入口，给玩家明确的信息，给玩家准备时间。
