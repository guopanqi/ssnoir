# 写Scenario

## Scenario回合与城市日期的边界

“多回合／多周期Scenario”按独立Scenario中的回合组织，使用 `start-scenario`、`define-opponent-rule` 和结果回调。
结束Scenario回合不推进世界日期；城市日期只控制进入窗口和未参与时的世界结算。
不能仅因为 Clock 可在世界模块中使用，就将Scenario替换为城市行动、世界换日加压或跨日任务进度。
第二幕 C1/C2 已由作者明确要求保留独立Scenario；这一边界优先于旧方案中关于“跨日”的表述。

## Scenario目标的固定位置

每场Scenario在根节点的直接子节点中放一条无空间锚点的 `note-node`，使用左上角的场景标注区展示当前目标。目标写玩家要达成的事情，不只写Scenario名称，也不能只在开场 Dialogue 中交代。它是只读标注，不是可点击动作。

```scheme
(container "醉客互相叫骂"
  (list
    (note-node "对骂：Scenario目标" "目标" "让两桌人都冷静下来")
    ...))
```

节点 Id 在整棵树中保持唯一；目标随阶段改变时更新这条标注，不叠加旧目标。不要挂到某张桌子或人物的子层里，也不要为左上角位置新增 Anchor 或坐标配置。

## 零、Scenario回应规则

世界日终继续使用 `define-turn-rule`；Scenario里玩家点「结束回合」后的场面回应使用
`define-opponent-rule`。两者不是同一套生命周期，不要混用。

`define-opponent-rule` 按文件中的书写顺序执行，一条规则就是一个因果批：后一条可以读取前一条已经
提交的状态，移动、拆分或合并规则因此可能改变结果。一条规则内部的 Scheme 状态修改正常顺序执行，
但客户端把这一条规则作为一个批次呈现；需要玩家分两步理解的先后因果，应拆成两条 opponent rule。

**一条规则就是玩家看见的一拍**，所以规则按"一拍一件事"来切，不按功能模块来切：

- 所有人的倒计时一起走一格 → 一条规则，三行 `advance!`。
- 某个人出手 → **他自己一条规则**，条件写清（还站着、倒计时归零）：扣冷静、重置出手钟，
  并在同一规则里登记表现这一击的短促 bubble。登记在代码前面不代表气泡在提交前出现。两个人的拳头
  一先一后，不在同一拍里糊成一团。
- 场外压力（艾迪撑不住、援军在路上）→ 一条规则。

### 持续规则：预告、发生、反馈

每条会影响决策的自动规则，作者须让玩家看清三件事：

| 层次 | 内容作者写什么 | 玩家看见什么 |
|---|---|---|
| 预告 | 节点存在时显示 `note-node`：时机、对象、变化；有触发条件或期限则一起写清 | 「回合结束：西边这桌愤怒+1」 |
| 发生 | 一条 `define-opponent-rule` 执行这一件事，条件与预告保持一致 | 这一回合只在满足条件时结算 |
| 反馈 | 同一规则里修改 Clock，并登记体现原因的短促 bubble | 醉客骂人，同时对桌愤怒上升 |

预告必须在进入该节点后仍能看见，不能只放在容器封面的副标题；目标变化时文字同步变化，效果结束时说明也消失。预告是作者写的规则说明，客户端不会从任意 lambda 推导它；修改效果时必须一起审阅说明。

人物持续行为每次发生都应有相应表现，不能只在首次出现时说一句，以后偷偷改数值。**不是每次变化都要说话**：自然衰减、时间流逝靠可见 Clock 的变化和脉冲呈现，不强加台词。Bubble 可以错过，规则所需的精确信息仍由常驻标注与读数承担。

例如「先骂人，再自行消气」若需要玩家分两步理解，就拆成按书写顺序执行的两条规则，预告同时写清两项；若只是同一件事的两个效果，可放在同一规则。作者举的假设不是正式玩法，不能顺手加进去。

### 新事件：说明与落点

会改变题面的新事件可用前置 Dialogue，然后 `(focus-node! 节点Id)` 提交新盘面、导航并等镜头到位，最后让新盘面上的人物用 bubble 表现情况。完整契约见 [表现时序](表现.md#什么时候播放决定了你能让谁说话)。空间表现已经足够清楚时可省略 Dialogue。

持续规则的普通结算不要每回合弹 Dialogue 或抢导航；只有玩家确实需要转移注意力的新变化才明确指定落点。不要用任意 `wait` 补救不正确的提交顺序。

**谁在动不用写。** 客户端拿这一批前后的两份快照按卡逐根钟比一遍，钟变了的卡就亮金边；
这一拍里开口的人也亮，气泡从他的卡上冒出来；主角的冷静掉了，冷静条旁飘一个 "−3"。
所以敌人的节点要叫他的名字（`"毡帽"`），不要叫动作（`"对付毡帽"`）——卡就是这个人。
他的生命钟就叫 `"生命"`，钟的身份靠它挂在谁的卡上，不靠标签里再写一遍名字。

```scheme
(define-opponent-rule "他们在逼近"
  (lambda () (not finished?))
  (lambda ()
    (approach! hat-life hat-attack)       ; 还站着且没归零就 (attack 'advance! -1)
    (approach! coat-life coat-attack)))

(define-opponent-rule "毡帽出手"
  (lambda () (and (not finished?) (standing? hat-life) (hat-attack 'empty?)))
  (lambda ()
    (play-bubble! (line "毡帽" "看哪儿呢。"))
    (hat-attack 'set! (hat-attack 'max))
    (spend-actor-composure! 'player 1)
    (play-bubble! (line "世界" "毡帽从侧面撞进来，肘子顶在你的肋下。"))))
```

前置阻塞剧情先播完，随后采用该批新快照，再播放气泡与变化提示；人物气泡不会抢在新状态之前出现。
没有玩家可感知内容的记账可以直接写在 rule 里；条件不成立、或什么都没改的规则不会在客户端
留下空拍，但其中的状态变化与Scenario终止仍然生效。时间税（每手扣一点冷静）由引擎在对方规则之前、和按键同一拍结清，脚本不用管；击穿倒下的，对方规则一条都不跑。

规则运行期间调用 `auto-action!` 只登记下一轮的强制行动。所有回应和回合末维护完成后，引擎先摇出
完整的新骰池，再按登记顺序用真实骰子逐个兑现 AutoAction；全部完成后，剩余骰子才交给玩家。
Scenario结束、主角倒下或切回世界会丢弃尚未兑现的登记。

`auto-action!` 自己持有卡出现后、抓骰前播放的前置对白；不要在它后面另写一段
`play-bubble!`，否则那段话属于登记 AutoAction 的对方回应批次，会在新骰出现前提前播放。
写法是：

```scheme
(auto-action! "主人过来敬酒" "他留住你们，说起昨晚的掌声"
  (list (list 'player 1) (list '夜莺 1))
  (auto-dialogue
    (line "主人" "昨晚那阵掌声，我隔着两条街都听见了。")
    (line "夜莺" "那您今晚站得近些。"))
  advance-all-crowds!
  "晚宴-沙龙")
```

没有对白时仍须显式传 `(no-dialogue)`。前置对白只负责表现；状态变化全部留在 effect 里。
客户端固定按“卡出现 → 前置对白 → 骰子入槽 → 执行与结果”播放，引擎则在提交这一批时已经完成
扣骰和 effect，因此完整播放与快进得到同一份状态。

## 一、入场与场内转场

- **场内转折按需要交代过程。** 走完路线、敌人出面、局面换幕可用 `play-dialogue!` 说明；
  已能从空间和气泡看懂的变化不重复讲解。阶段状态在引擎执行时就已更新，何时显示由提交边界决定，
  不是把赋值挪到 Dialogue 后面就能推迟显示。要在同一串剧情中让新盘面接管，使用 `focus-node!`；
  提交前后的角色锚定约束见 [表现.md](表现.md)。
- **`spotlight!` 只宣告结果。** 它适合Scenario成功 / 失败 / 阶段结算这类告示卡，不承担人物对白，
  也不拿来替代换幕过程。
- **入场摆盘面用 `'load!`，不用 `'set!`。** `on-scenario-enter` 里把钟拨到初始格是摆盘子，
  不是玩家造成的变化；`'set!` 会写进发起Scenario那个世界动作的报告，点进去先弹一张空的
  行动结果（曾经实测漏出过"踪迹 +3"）。`'load!` 静默设值，越界直接报错，正好拿来做初始化。
