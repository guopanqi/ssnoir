# 数字命运骰结算实施计划（方案B）

> 与 [命运骰结算实施计划.md](命运骰结算实施计划.md)（方案A·记号骰）互为**二选一**的
> 备选方案，两者只实施其一。共同点：单一随机源、技能 0 基、投入不清零、越界永
> 无零风险。差异：本方案保留一颗**全游戏唯一的 1–6 数字命运骰**，风险用修正表达
> 而非换骰；直观性由「命运条」UI 承担。
> 设计动机与推导同见方案A §0.5，2026-07-11 讨论定稿。

## 0. 规则定稿

### 0.1 判定公式

```
总和 T = 放入骰 + 命运骰(d6) + 技能 + 修正        （技能从 0 起）
T ≤ 6 → 坏      7–8 → 中      T ≥ 9 → 好

天然面规则（看命运骰的原始面，与 T 无关）：
  命运骰天然 1 → 结果降一档（好→中，中→坏，坏不再降）
  命运骰天然 6 → 结果升一档（坏→中，中→好，好不再升）
```

- 命运骰的点数**照常参与 T**，天然面规则是叠加在最终档位上的第二步。
- 升降是**档位操作**而非数字加减：天然面每次触发都恰好改变一档，玩家一定看得见。

### 0.2 风险与修正

风险级由 `工作` DSL 注入固定修正（这是方案B与方案A的核心差异——风险住在修正里）：

| 风险级 | 修正 |
|---|---|
| 低 / 中 | 0 |
| 高 | −1 |
| 越界 | −2 |

情境修正（通行证 +1、风声紧 −1 等）继续走 `roll` 的 mod-fn 回调，与风险修正叠加。

### 0.3 概率梯子（校验基准）

令 **B = 放入骰 + 技能 + 修正**（放骰后确定可见）。最终分布只由 B 决定（坏/中/好 %）：

| B | 坏 | 中 | 好 | 说明 |
|---|---|---|---|---|
| ≤0 | 83 | 17 | 0 | 天然6把绝境捞到中 |
| 1 | 83 | 0 | 17 | 天然6直升好：烂骰的「撞大运」 |
| 2 | 67 | 17 | 17 | |
| 3 | 50 | 33 | 17 | |
| 4 | 33 | 33 | 33 | 中枢 |
| 5 | 17 | 33 | 50 | |
| 6 | 17 | 17 | 67 | 天然1把中拽进坏 |
| 7 | 17 | 0 | 83 | |
| ≥8 | 0 | 17 | 83 | 坏消失，天然1只咬到中 |

抽样验证（走私：越界 −2，敏锐）：
- 生手（敏锐 0）放 6：B=4 → 33/33/33，掷硬币。
- 老手（敏锐 2）放 6：B=6 → 17/17/67——与方案A的老手走私**完全同点**，两案调向同一目标。
- 刷盘子（低风险 0）生手放 6：B=6 → 17/17/67；熟手（技能 2）放 6：B=8 → 0/17/83。

### 0.4 取舍（相对方案A，如实记录）

- **保住的**：全游戏一颗骰、一条规则，无词汇表；数字可加性完整——任何新难度
  都只是又一个 ±n，内容扩展零成本；带内「差一点」的邻近感保留。
- **付出的**：天然1对所有动作一视同仁——生手做低风险活放 6 也有 17% 坏
  （B=6 行）。低风险坏结果本来很轻（+1压力），先接受；实测嫌烦见调参旋钮。
- **边界注意**：B≥8 后坏消失。越界 −2 时 B=8 需要 放入6+技能4（满级+最好骰）
  才达到，全程几乎摸不到；若不可接受，旋钮里有两个办法。
- B=1、B=7 两行没有「中」（天然面把唯一的中带面搬走了），是天然面规则的
  特征纹理，非 bug。

### 0.5 留白（本期不做）

- 天然1/6 触发时的专门演出（先用文字与色彩重音）。
- 手牌按选中动作的 B 值整体染色（后续打磨）。
- 封顶天然6的小溢出奖励。

## 1. 阶段一：引擎判定层

### 1.1 新类型（Engine/Runtime/Core）

新建 `FateStrip.cs`，替换并删除 `RollOdds.cs`：

```csharp
public static class FateStrip
{
    // 判定与预览的唯一共用数据源：
    // 对命运骰六个面，逐面算出最终档（含带子判档 + 天然1/6升降 + 夹紧）。
    // strip[i] = 命运骰掷出 i+1 时的最终结果。
    public static RollOutcome[] Compute(int placedDie, int skill, int modSum);

    // 单面判定（SceneManager 用）：等价于 Compute(...)[fateDie - 1]
    public static RollOutcome Resolve(int placedDie, int skill, int modSum, int fateDie);
}
```

**判定表即预览表**：SceneManager 掷出 D 后直接查 strip——预览和结算在结构上
不可能不一致，这是方案B工程上最优雅的一点。

### 1.2 判定分支重写

[SceneManager.cs:588-628](../Engine/Runtime/Core/SceneManager.cs) Roll 分支改为：

```csharp
int fateDie  = rand.Next(1, 7);
var strip    = FateStrip.Compute(chosenDieVal, skillLevel, modifierSum);
var outcome  = strip[fateDie - 1];
```

- 技能查找保留「未知技能抛异常」断言，允许 0。
- `ActionReport`（[ActionReport.cs](../Engine/Runtime/Core/ActionReport.cs)）调整：
  - 保留 `ChosenDieValue`、`DifficultyModifiers`、`Outcome`、`FinalRollValue`
    （= 命运骰面，滚动动画仍要它）。
  - 新增 `int BaseSum`（B 值）、`RollOutcome PreShiftTier`（天然面生效前的档）、
    `int NaturalShift`（−1/0/+1，供 UI 判断是否播天然面重音）。
  - 删除 `ModifiedRollValue`、`RandomDice`（编译错误即消费点清单：
    RendererState / RaylibRenderer / OverlayWidget / IMGUIAnimationPlayer /
    CardWidget / ActionNodeDrawer）。
- `PresentationHint.RollDice` 携带（命运骰面、天然位移、最终档）。
- `GameResolve`、`NodeConverter` **零改动**（无骰类概念，方案B比方案A少一层）。

## 4. 阶段四：UI——「命运条」（本方案直观性的承重墙）

### 4.1 卡面预览（放骰时）

TerminalApp [CardWidget.cs:408-483](../TerminalApp/src/Rendering/CardWidget.cs) 与
Unity [ActionNodeDrawer.cs:580](../UnityClient/Assets/Scripts/Runtime/IMGUI/Components/ActionNodeDrawer.cs)
两处镜像同步改。删除三色概率条 + 百分比，换成：

```
命运条：一行六格，格内写 1–6，每格按 FateStrip 的最终档染色
        （坏=红 / 中=黄 / 好=绿，沿用现有 Odds 三色）。
        天然面规则改变了档位的格子（1 或 6 号格），在角上加一个
        小三角标记（1=深色角标「降」，6=亮色角标「升」）。
摘要句：格子上方一行小字，如「命运骰 3+ 即好 · 1 则坏」，
        由 strip 自动生成（找出各档的边界面）。
```

原则：**染的是天然面规则生效后的最终结果**——玩家永远不需要回忆规则，
看格子颜色就是全部真相。改放入骰 / 换角色 / 修正变化时命运条实时重算。

### 4.2 结算动画（掷骰时）

- `DrawLocalRoll`（[CardWidget.cs:485](../TerminalApp/src/Rendering/CardWidget.cs)）与
  Unity [IMGUIAnimationPlayer.cs](../UnityClient/Assets/Scripts/Runtime/IMGUI/IMGUIAnimationPlayer.cs)：
  滚动阶段在命运条上快速跳动高亮，定格在掷出的格子上；格子颜色即结果。
- 明细行：`基础 7 + 命运 4 = 11 → 好`；天然面触发时改为
  `天然 1 · 降档 → 坏` 并给红/金色文字重音（`NaturalShift` 字段驱动）。

## 与方案A的选择要点

- 两案在关键锚点（老手走私 17/17/67）上同点，手感目标一致。
- 选 **A（记号骰）**：要「风险是一个看得见的物件」「掷骰时刻零算术」，
  接受 4 记号 2 骰的固定词汇表。
- 选 **B（数字骰）**：要「全游戏一条规则」「数字可加性带来的免费扩展」，
  接受直观性依赖命运条 UI、天然1对所有动作一视同仁。
- 工程量 B 略小（无 GameResolve/NodeConverter 改动、无骰类枚举），
  UI 工作量两案相当（刻面行 vs 命运条，同一位置同一复杂度）。
