更新：2026-10-12。目标是在不牺牲证据质量的前提下同时推进不同的抽象决策关系，而不是让多个工作者轮流修改同一份规则。

## 能力与角色

- **研究协调者**：选课题、阅读最新证据与真人反馈、分配互斥目录、审查方法与重复性、集中修改共享记忆/队列/工作台；唯一拥有候选晋升裁决权。
- **独立研究工作者**：冻结同一来源版本，只修改本任务脚本和私有批次记录；先写可能推翻自己的强基线与禁用新增规则消融，再报告正常策略路径及边界。
- **反证工作者**：用独立实现或数学手算检查概率、可达性、同值规则与统计口径；不能直接复制研究者结论当独立证据。
- **真人审阅**：异步，通过已有研究工作台反馈；不作为自动计算继续推进的前置条件。

本次 R103–R105 使用 **GitHub Actions 三个独立并行执行 Job**（数学校验），不是三个独立 LLM Subagent。当前聊天工具没有启动多个具独立上下文的 LLM Subagent 的直接接口。未来若接入可委托的 coding-agent/orchestrator，仍应沿用这份隔离与集成契约，不能因为它叫 Subagent 就降低证据门槛。

## 启动每条研究线的输入

为每条研究分配唯一编号和目录，冻结：基础版本 Git SHA、一个决策关系、公开状态及可行动作、目标/结算函数、一个显然可能解释结果的简单策略、直接关闭新增规则的反事实、期望出现的严格自愿改变与停止条件。缺少其中任何一项则先纸面排除，不建立实验场景。

研究者的原始脚本保存在 tools/content-validator/experiments/rNNN_*.py，结果在独立 Actions Artifact；批次写自己的研究记录。原始 Unity/Scheme 场景不因试验方便而被覆盖。比较固定 seed 的原生分支，除非显式锁定完整外生随机流，否则绝不称为严格同随机结果配对。

## 并行执行与整合

1. 不同假设、文件和 Artifact 在各自的 Job / 分支中并行。不同 Job 不修改共享状态文件或 Debug 清单。
2. 各 Job 应用独立校验，失败不得被其他 Job 的成功掩盖；保留完整原始输出。再由协调者审查与既有 R 轮的同构/重复。
3. 只有协调者在读完全部结果后更新 自主研究记忆.json、研究队列.md、当前状态.md、模式库.json，并生成/验证 HTML 研究总览。
4. 数学“可达严格有利”、正式 C#+Scheme 技术因果、真实人类有意识的选择是三个不同层次；不跨级称为好玩。
5. 原生研究与真人反馈成熟度不足，不得将原型自动加入 DebugResearchPlaytests.json；候选库不为凑整数而晋升。
6. 同期其他 agent 已提交代码时，提交前再次读取 main HEAD 与当前记忆，避免覆盖历史。研究编号一旦撞号，追加来源后缀而不是覆盖另一方证据。
