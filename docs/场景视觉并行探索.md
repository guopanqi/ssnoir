# 场景视觉并行探索

**状态：2026-10-05 暂缓，优先完成更重要的游戏任务；本轮候选未采纳，未接入正式资产。**

这是现有场景改造的试行流程。探索阶段不提供认可参考图或共同视觉基准；共同基准仅在评审阶段使用。不是要求不同场景都像夜城，也不是由 Agent 自行判定可以发布。

## 优先方案：沿用现有语言补齐交锋场景质感

2026-10-05 补充：后续先尝试这一范围更小的方案，自由探索保留为较后的选项。本次只记录，不启动新的并行任务；仍待高优先级任务完成后安排。

使用 **GPT-6.1 Sol light** 并行处理不同交锋场景。此方案从一开始就读取现有设计语言、共享视觉基准和正式实现，与后文的盲式自由探索不同。目标是补齐现有空间缺失的表现，而非重新设计空间或发明新的呈现功能。

重点检查与调整：

- 描线层次：关键对象、主要结构、次要细节和背景是否有清楚的线条主次，避免全无边线或所有线同样抢眼。
- 光影：用现有光源与材质角色组织主体、环境、前后层次，让交互相关对象可读，同时保留场景应有的情绪。
- 适当调色：在现有机制允许的场景局部参数内调整冷暖与氛围；不能以局部调色之名修改全局基准，也不能复制一套共享材质来绕过审核。

这里的“色盘”泛指**共享视觉基准参数**：材质颜色、反光与粗糙度、描线材质、镜头冷暖、整体调色和氛围等，不仅是一组颜色。某个参数是否共享，以实际资源引用和作用范围为准，不以文件名或当前只打开一个场景判断。

共享基准默认只读。通常应先用现有语言解决问题；只有 Agent 有明确、强烈的理由认为现有基准无法表达该场景时，才提出修改建议。建议须说明具体缺口、拟改参数、为何局部调整不足，以及对其他使用场景的影响，并给出隔离副本中的对照。**审核通过前不得修改正式共享资源**；单场景看起来更合适不足以成为全局修改的依据。

轻量流程：读取剧情、玩法、原空间和现有基准 → 每个 Agent 在独立副本中补齐表现、自主迭代 → 主 Agent 汇总原版与实际 Unity 候选画面，检查语言一致性和共享资源影响 → 玩家审核 → 接入通过的局部方案。保留既有玩法、镜头和锚点契约，不顺带扩大为布局重建或新功能开发。

每份交付只需说明“原来缺什么、改了什么、为何更清楚”，附相同机位的前后图、所用材质/光源角色、局部参数及实际验证范围；共享基准建议另列，不夹在场景修改中。先以少量场景试行，观察质感提升、审核成本与耗时，再决定是否扩大。范围更明确预计能更快收敛，效果与效率仍由实际试行判断。

## 四个阶段

1. 读剧情、玩法和原空间：明确玩家应该感受到什么、首先看到什么，区分脚本已经确定的事实和创作者的解释。
2. 自由探索：独立副本中调整布局、配光、建筑与道具，制作、渲染、自审、淘汰失败方向，寻找最适合故事的空间设计。不要阅读其他候选或认可参考图。玩家授权此阶段自主迭代，不按从零做场景 Skill 的每个中间确认门逐步停下来。
3. 汇总审核：探索完成后，主 Agent 再对照游戏的共同视觉语言，判断可直接表达、需要用现有角色转译，或需要扩展语言。无新元素也由玩家审核后开工；有新元素时给出原版对照、实际 Unity 候选图和取舍理由，由玩家决定采纳、保留部分或改变方向。
4. 制作与接入：通过后落实正式源，检查镜头、锚点、相邻场景、共享材质与实际游戏效果，再请玩家最终确认。

探索候选可以是可运行的 3D 空间，审核前渲染到隔离 Unity 工程不等于正式接入。不能只交概念图就声称游戏效果已成立。

## 输入与隔离

探索 Agent 仅拿到本场景的剧情、玩法、原空间与必要技术契约。上世纪美国港口城市和黑色电影是世界事实；色盘、认可图和具体描线配光偏好不作为探索输入。原有资产上的痕迹无法消除，但不主动强化为范本。

每个 Agent 独立目录/工程，输入只读，修改、输出与日志只写自己的工作目录。主项目、独立 CityBox 仓库及其正式模型、全局 Shader、共享色盘不可写。保留名称、Anchor、镜头类型与输入能力契约；可以提出移动锚点，但不可自行改游戏规则、对白或动作费用。布局提案可以改建筑内部；需要改变城市布局时单独声明。

主 Agent 负责 Unity 候选渲染与审核、共享资源提案、最终整合。Unity 工程/Library 不由两个进程共同使用。同一个生图服务 profile 不能并发；本轮默认用现有几何和程序化构件，不新增付费生成用量。

## Agent 交付

- 原空间基线图、一个明确推荐的完整空间方案与补充机位；可复跑脚本、候选 `.blend` 与语义节点。
- 情景理解：剧情依据、玩家注意力顺序、空间如何支持动作/冲突。
- 取舍：自主观察发现的问题、实际做过的修订、舍弃方向与理由。
- 元素清单：故事必须的、新增但可选的、可能要求新视觉语言的，分别记录。
- 技术边界：保留的互动契约、实际检查与未检查项、Unity 接入工作和风险。

主 Agent 不能为了迁入方便，在玩家审核前悄悄把自由方案改成现有风格。需要转译时展示转译结果，并保留原探索结果。

## 审核标准

首先判断故事表达是否成立：第一眼能否读出关键空间，场景是否支持脚本里的行为，是否把不存在的情节当作事实。其次检查游戏视角下能否阅读，包括 UI 占位、镜头移动和交互落点，不用单张漂亮构图代替可用空间。

最后才检查语言一致性：哪些几何、光源、表面、描线、动态元素可用现有角色实现；哪些只是参数微调；哪些会影响全局共同基准。新道具不自动等于新视觉语言；沿用旧资产也不自动意味着一致。新共享角色或 Shader 的提案要说明旧方案的具体表达缺口、最小扩展及对其他场景的影响。

玩家审核的是推荐方向、必需的新元素与真实 Unity 画面。技术或审美仍有不确定性时明确标出，不把主 Agent 的判断冒充玩家认可。细节通过统一编辑器参数由玩家微调。

## 本轮结论与重新启动的边界

用户原本希望替换建筑在世界中的表现，本轮任务却允许较多内部重构，警察局最终成为室内剖面设计。室内设计有可读的空间关系，但没有回答世界建筑替换的问题；不能用独立画面的好看代替任务完成。诊所侧重入口与配光，也尚未达到游戏的设计方向。本轮不继续打磨或申请接入。

后续重点改为**交锋空间**：它们更适合故事驱动的布局探索；城市建筑受到尺寸、街区衔接、世界轮廓与已有机位等约束，当前改造收益有限。已调整过的晚宴、别给他们想要的、码头先不重复制作。重新启动时先明确任务是世界外形、地点近景还是交锋舞台，再派发，防止任务对象漂移。

“城市显示外壳，聚焦或交互时揭开外壳呈现内部”保留为将来可讨论的构想。它是新的呈现功能，不是本轮接入的默认前提，不实施、不加入本轮技术范围；只有核心游戏需求明确时再判断必要性。

自由探索仍不预先提供认可参考图或共同色盘，共同基准放在审核阶段。必要的题材、目标、空间职责和交互契约应提前明确。探索不等于重新制定游戏风格；审核发现方向不合时可以淘汰方案，不必为了挽救实验新增系统。先审核方向，再制作经审核的正式视觉版本，最后审核实际游戏效果。
