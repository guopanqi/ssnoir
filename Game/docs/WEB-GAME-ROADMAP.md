# SSNoir Web Game — 长期目标与阶段路线

## 项目定位

Game/ 是基于 SSNoir 既有 Scheme 内容扩展出的独立 Web 游戏项目，而不是 Unity 移植项目。
最终目标是一部 **从新游戏开始、能完整经历角色故事、行动/交锋、昼夜循环、演出、结局、存读档的可玩游戏**，并拥有供 Agent 重复测试的实验入口。

- Unity 正式客户端的 feature freeze 不约束 Game/ 的实验建设。
- 内容唯一来源暂时仍为 UnityClient/Assets/Resources/Content/**/*.scm；第一阶段严格不编辑这些 .scm。
- Runtime 复用 Game/src/runtime 和 Game/src/scheme；不追求所有 C#/Unity 视觉 API 的逐项移植。
- 不是两套游戏规则：Web 前端不能硬编码事件进度、数值变化或脚本后果。
- 初期只为现代浏览器开发；微信、TapTap、Electron 的适配链路不作为 Web 游戏验收条件。
- 每次迭代优先形成可玩的真实情境，不以 screenshot、build 通过替代游戏体验。

## 工程质量原则（适用于 Web 全阶段）

- 以可玩的真实体验为中心，同时追求长期清晰、可靠、易扩展的工程；不把最小代码量、最快提交或某一条路径短暂变绿当作目标。
- Scheme 是规则和叙事状态的权威来源，Runtime 负责执行与持久化，Web Session 只承接命令与只读投影，React/Three.js 不产生游戏后果。
- 相同规则和状态变迁应有单一所有者。重复路径应统一、临时兼容应有明确退出条件；未知或错误配置明确失败，不容忍静默补值。
- 以可审阅、可回滚的阶段控制风险，但允许为根因修复调整跨模块抽象；同一阶段必须有契约测试与真实玩家浏览器流程的证据。
- 不凭相邻阶段的测试通过推断完整可玩；明确记录未覆盖的失败、分支、对话与镜头演出行为。

## 目标架构

Scheme 原内容 -> 隔离的编译式 Scheme VM / native bridge / SceneDirector / ActionRunner
-> WebGameSession（异步命令 + 纯展示快照 + 叙事队列）
-> React（HTML/CSS：骰子、行动、时钟、卷宗、对话）
-> Three.js（独立画面视口：城市、地点、镜头、动画）
-> Playwright（真实浏览器交互和可重放实验证据）

Runtime 对前端提供状态和命令；Three.js 不负责决定游戏状态，React 不执行 Scheme。
同一个 Session 未来还可被 Agent 通过无头调用方式控制。

## 阶段（每期必须有可复查产物）

### P1 可操作的 Web 竖切片（已通过真实浏览器闭环验收）
- 固定 Scheme 内容不变；保留现有 Runtime 和旧移植资产作为历史参考。
- 建立 WebGameSession 与新浏览器入口，隔离运行时和表现。
- 浏览器可打开原始 world.scm 的城市和地点，看到真实行动与骰子、执行原始行动、换日、浏览简化剧情。
- 支持基本存读档；构建独立 Web CI 和浏览器截图烟测。
- 验收：真实第一幕可以从第 1 天进入一个地点并进行行动、返回城市、换日；浏览器 UI 不调用旧 foundation/render.ts。

### P2 玩法完整性与可靠性
- 完整呈现节点语义：多骰/多角色、物品投入、Clock、风险、记录、交锋与对手回合。
- 对话、状态、卷宗/未读内容、行动反馈和必做事件能正确区分并表达。
- 用当前正式内容建立有意义的通路测试，修复 Runtime 与 Scheme 行为偏差。
- 验收：第一幕从新档到幕末稳定完成；关键失败路径、读档和情境切换有回归测试。

### P3 戏剧表现与空间
- 建立可配置场景布局、镜头、视觉风格，使用 Three.js 表达城市/地点。
- 把 Stage/Theatre/Dialog/Camera/Spotlight 事件呈现为可阅读、可操控的演出。
- 先做少数关键场景，用共同组合语法扩张，不把视觉硬编码进游戏逻辑。
- 验收：剧情关键情绪节点有可理解的空间与演出表达，不再显示原始命令列表。

### P4 Agent Gameplay Lab
- Playable Fixture：固定剧情状态、角色、骰子与随机种子的情境入口。
- 自动执行行动轨迹、记录状态差异，截图/trace/决策日志支持并排对照。
- 能把规则、目标结构与视觉表现分别调整并回归，加入针对高价值场景的实验测试。
- 验收：同一情境可稳定复现；玩法变更的实际行动及后果可对照。

### P5 内容覆盖与游玩闭环
- 把当前 Scheme 的章节、人物线、城市事件和 Scenario 接入可玩的浏览器流程。
- 补齐断线、无法恢复的失败、关键内容遗漏、章节转场与结局。
- 完成连续存档、游戏恢复、输入体验、性能与错误提示。
- 验收：从标题开始到当前作品最后一章/结局，无需开发者命令或手动改变量。

### P6 体验打磨与验收
- 玩家试玩观察：决策理解、剧情参与、节奏、情绪、信息可读性。
- 聚焦反复出现的实际痛点，逐项调整视觉、行动、反馈与内容组织。
- 浏览器正式可玩构建、自动化核心路线及手工完整游玩均通过。

## P1 连续游玩验证记录

浏览器用真实的 Scheme 内容（固定随机种子 42）完成以下可复现路径：

1. 城市 → 家；验证初始「旅馆清晨」声明的必做阻塞。
2. 执行「旅馆清晨」；解除必做阻塞，开放酒馆。
3. 返回世界 → 进入老街酒馆 → 看场子；投入一枚真实骰子，核对消耗与结算。
4. 保存原始 Scheme 世界和 native 状态。
5. 返回旅馆 → 住宿 → 睡觉；由 Scheme `end-turn!` 触发世界换日，不由 UI 强制推进。
6. 验证新日骰子重新投掷，从存档恢复之前世界日期、库存和节点。

世界必做事件由节点树 `:required-before-rest` 投影，而非 UI 手写规则；
该投影与 C# 相同，发生变化时二次生成节点树，使睡眠节点状态一致。
`Game/scripts/smoke-web.mjs` 应以 Playwright 真实浏览器按钮执行这条路径并截图。

## P1 解析器追平记录

当前 Scheme 节点已使用 `:display`、`:notice-version`、`:use-limit`，
Web NodeConverter 需要严格解析并保留这些字段，并兼容最新十字段 Clock（增加 reset sequence/from）。完整“未读”标识和 daily-once 规则消费属于 P2。

## 已识别的跨语言语义缺口（非 P1 验收）

旧全量 `npm test` 的 `native-contract.test.mjs` 检查目前失败：
C# 新增 `__bubble-restore-composure`，TypeScript 的 NativeBridge 没有对应实现。
该能力的 C# 语义是在气泡台词真正展示时恢复冷静，不是在脚本读取时立即恢复；
禁止只补一个空壳注册来欺骗测试。P2 需要连同气泡播放生命周期正确实现。

P1 的 `npm run test:web` 仅检查 WebSession 和当前第一幕基础内容，
不声称跨语言完整 parity。旧 `npm test` 保留为未消除的兼容性诊断。

## P1 明确不做
- 不调整任何 .scm 剧情/规则。
- 不为微信/TapTap/Electron 解决平台问题。
- 不重建 Unity 的复杂镜头和场景资产。
- 不用伪造行动成功或客户端本地状态代替真实 Scheme 状态。
- 不宣称第一阶段就具备后续完整演出或完整玩法。

## 技术判断
- Vite + TypeScript：继续复用现有构建和类型化 runtime。
- React + 浏览器 HTML/CSS：快速组合信息密集的游戏 UI；避免在 Pixi 内手工排版文字、滚动、交互。
- Three.js：只负责需要空间的游戏画面，不和 UI 争夺输入和状态。
- Playwright：以真实玩家路径、截图、状态检查和 trace 验证。
- Web 游戏使用隔离的 BiwaScheme 编译式 VM；原始 LIPS 仅保留为历史底座探针。此次替换基于端到端性能及状态对照，见文末记录；不维护两套游戏规则。

## 优先级原则
架构应该为故事和玩法节省迭代时间，而不是成为独立的长期技术实验。
完整可玩性与玩家实际体验始终高于跨平台、额外框架和表现功能数量。

## P1 真实浏览器暴露的语义差异

打开老街酒馆后出现的「点一杯酒」是无风险 Instant 行动，但带有 `:progress-target (list 'composure "player")`；
C# NodeConverter 允许此组合，旧 TypeScript 错误限制了必须带 `:risk`。
现在效果目标可独立于检定风险；世界根 `世界` 的 `:arrivals` 也按 C# 例外保留。
这两项都属于原有 DSL 语法，不改动 Scheme。

## P1 验收结果与 P2 性能门槛

- [Web CI #41771715854](https://github.com/guopanqi/ssnoir/actions/runs/41771715854) 成功，18/18 个专项测试通过。
- Chromium 用真实 Scheme 完成：旅馆清晨 → 酒馆看场子 → 消耗骰子 → 存档 → 睡觉进入第 2 日 → 读档恢复第 1 日和金额；五张截图已归档。
- 读档从触发到完全恢复在 CI 中约 77 秒，属于已证实的严重性能缺口，不能作为正式可玩体验接受。
- P2 优先把耗时拆分为 bootstrap / world-load! / render 三阶段测量，逐项优化，仍保留原始存档的失败不损坏旧状态保证。
- 在读档性能达到正常可用水平之前，不把 P1 构建称为发布版游戏。

### P2 读档优化 1：跳过即将被存档覆盖的初始建树

读档时始终新建独立的 Scheme 世界以维持原有的失败隔离，但新 VM 的初始骰子和初始渲染树随后都会由存档覆盖；因此仅针对读档的 `GameSceneDirector.create(..., false)` 跳过首次掷骰与 `actions.prepare()`，在 `world-load!` 后仍完整执行一次权威节点重建。普通新游戏路径保持不变。通过浏览器完整读档回归才能验收此优化；不得绕过 `world-load!` 或存档校验。

### P2 读档优化 1 的 CI 验证

- 未优化：98.8 秒（初始化 15.7 秒、数据读写与模块恢复 69.8 秒、建树 13.3 秒）。
- 跳过冗余初始建树：[Web CI #41772805092](https://github.com/guopanqi/ssnoir/actions/runs/41772805092) 通过全部 18 项测试及真实浏览器回档；总耗时 86.9 秒，其中初始化 5.0 秒、数据读写与模块恢复 68.7 秒、建树 13.2 秒。
- 瓶颈仍是中间环节；下一步将 `read (open-input-string ...)` 与 `world-load!` 分开计时。两条命令依然在同一个新的 LIPS 解释器执行，原始 Scheme 内容不变。临时绑定只存活到恢复完成。

### P2 读档优化 2：加速字符串键的关联表查询

本机剖析确认 6,162 字符的存档 datum 读取只需约 37 毫秒，主要开销来自各模块 `load!` 中反复解释 `assoc-get` 的递归与 `equal?`。现在由 LIPS 适配层直接遍历字符串键；其他键继续使用原 Scheme helper，保留完整相等语义。每次读取当前列表，不缓存可变数据，不改变 Scheme 内容、存档格式或 `world-load!`。

- 同机真实浏览器路径：读档总耗时由 36.6 秒降至 10.4 秒；模块恢复阶段由 28.8 秒降至 2.7 秒。属于本机单次对照，不能代替 CI 或低端设备的性能结果。
- `npm run verify` 通过类型检查、生产构建和 23 项测试，新增查询语义对照及真实世界存档往返检查；另通过 6 项 Runtime 测试。
- 浏览器完成原 P1 全路径，并额外验证损坏日期存档被拒绝后，当前日期、资源、骰子、人物、必做事件及节点保持不变；有效读档恢复未花骰及槽位身份。
- 下一处主要开销是恢复后的权威建树（本机约 5.6 秒）；仍不视为发布版体验。证据见 [读档性能验证](../../artifacts/工程验证/SSNoir-Web读档性能/README.md)。

### P2 可见玩法信息：卷宗与行动反馈

- Web 的卷宗按钮直接读取 `WorldHost.getDossier()`，显示当前 Scheme 模块定义的故事线、主次、状态、当前目标、指路与 Clock；待办仅公开第一项未完成任务，不提前泄露未来任务的文案。
- 每次真实 ActionRunner 结算用 `ActionResult.before/after` 计算冷静、伤势、物品和成长的实际变化，并用原始 `clockEffects` 显示 Clock 的增减；骰子投入也显示为实际行动资源成本。成功/一般/失败会翻译为中文，不再展示内部 `fail` 字符串。
- 所有结果只是展示层投影，不能写入游戏数值、改变结果或推进情节。与新视觉面板相对应的 WebSession 单测及 Playwright 现实内容烟测必须通过。
- 尚未支持复杂 Stage/Theatre 的实际动画演出、未读变化、完整第一幕通关等，仍按长期路线逐项验收。

### P2 权威节点建树优化：原生基础 membership helper

继续沿用 Scheme 的 `get-render-data` 作为唯一生成入口，**不缓存、裁剪或跳过 authored 节点**。由于世界场景及人物会反复执行项目 stdlib 的递归 `member?`，Web LIPS 桥接只对字符串及 Symbol 成员判断执行原地链表遍历；复合值、数字与布尔值全部交回原 Scheme 原函数处理。输入始终读取实时节点，不会因人物状态或列表修改而使用过期缓存。配套测试覆盖 Symbol 与字符串不同类型、复合键匹配及可变列表。真实浏览器全路径与 CI 基准决定是否保留此优化。

### P2 对话语义修复

Web StoryPlaybackQueue 现在识别现行 `engine.scm` 的 `line` 七字段结构（identity、text、voice、dwell、stage、display、anchor）以及带额外 appearance 的八字段结构。显示说话人使用 `display`，对白内容只使用 `text`，而不是把声音、舞台指示、锚点和文本拼成一行。原有旧格式 `line` 标签测试仍保持兼容；这只更正表现解析，不改台词脚本或结算。

### P2 第一幕新档至告别演出通路

- 新增 `Game/scripts/first-act-route.mjs`，Chromium 从原始 Scheme 清晨新档逐日睡觉至第 6 日，检查第 5 日告别公告、第 6 日必做的告别演出与 `act=2` 对应的卷宗结束。
- 首次 [Web CI #41776575103](https://github.com/guopanqi/ssnoir/actions/runs/41776575103) 实测：第 2 天再次进入旅馆，「睡觉」仍 disabled。原因是新日仅刷新世界节点，未执行 `on-enter-place \"世界\"`，未解除原脚本的「出门才能再睡」锁；这是真实客户端缺陷。
- 修复沿用 Engine `SceneManager.EnterPlace` 的现有契约：世界根与地点共用入场动作，自然醒来和返回地图均执行 root arrival，使连睡锁正确解除，同时播放第 5 日一次性告别公告。
- 若房租不足，长通路使用原脚本提供的「蜷缩在门口」合法过夜，不注入金钱、跳日或篡改 Scheme。

### P2 气泡展示时才恢复冷静

Web NativeBridge 正式承接原脚本的 `__bubble-restore-composure`：仅将冷静恢复的角色、数值、通知、生成世界日及唯一标识附加于一条七／八字段台词的序列化元数据，不在执行 Scheme 时直接修改冷静。Web 叙事队列将非阻塞气泡保留至阻塞对白完成，再在该句被当前界面呈现时兑现；跨日丢弃、同标识只结算一次，场景出错或存档恢复不会提前补发。与 C# 保持同一关键语义：不展示就不兑现，尽管当前 Web 尚未实现逐句定时气泡的空间表现。

### P2 第二幕彩排 Scenario 通路（续测）

[Web CI #41777441444](https://github.com/guopanqi/ssnoir/actions/runs/41777441444) 已通过 34/34 项测试，浏览器从原始第 1 天连续进入第 6 天，播放第 5 天一次性告别公告，完成第 6 天强制演出并核对卷宗结案。恢复后权威建树为约 5.9 秒，总读档约 11.3 秒；这些是一次 CI 环境测量，不以此替代正式交互验收。

在同一浏览器通路上追加第 7/8 天的合法过夜、第一次彩排强制赴约、Scenario 分配骰子、五回合推进及场景回归，校验最初的城市循环是否能正确衔接另一种 Gameplay 形态；本部分需等新增 CI 验收，不预先宣称完成。

### P2 真实 Scenario 的 Clock 可读性修复

原 Scheme 的 `clock-nodes` 生成带 `:resolve (clock ...)` 的标注节点，Web NodeConverter 已解析为 `resolve.noteClock`，但 WebGameSession 此前只映射 `:clocks` 数组，导致彩排的「歌曲进程」「布景就位」「灯位标记」无法显示实时进度条。本次仅修正 ViewNode 投影，兼容容器 Clock 与独立 clock-node，既不修改任何 Scheme 时钟，也不额外计算进度；在现有第八天真实 Chromium 彩排路线和 WebSession 单元测试验证可见性。

### P2 对手回合成本和后果的可见反馈

原 Web 的 `endTurn` 执行五回合彩排时只显示「交锋进入下一回合」，并清空此前行动反馈，玩家无法从结算提示判断冷静耗损及其他资源变化。现在对每次 `GameSceneDirector.endRound()` 前后的真实 `GameRuntimeState.snapshot()` 做同一展示层差值投影，显示冷静、伤势、金钱等实际变化；不推断或修改任何规则，也不伪造 Clock 增量（时钟仍由作者的进度条直接显示）。新增 WebSession 单测以及真实第八天彩排五回合路线断言。

### P2 底层性能根因修复：节点关键字查询

### P2 共同执行路径重构：隔离的编译式 VM

先确认 `a57ff5d8` 的 Web CI #41806759784 已成功。其关键字 helper 优化有效但不足：本机原始/优化建树仍约 7.0/5.4 秒，进入有入场事件的地点需要两次权威建树。

本轮不继续把 `node`、Clock 或剧情模块翻译成 JavaScript，也不缓存世界树。Web 运行时改用固定版本 BiwaScheme 的编译/宏展开及字节码执行。每个世界、Scenario 和读档候选独立拥有 TopEnv、CoreEnv、Compiler 和执行状态；仅 Pair、Symbol 与空值等数据类型共享。构建从依赖中提取无浏览器启动副作用的内核，以源 SHA-256 校验隔离边界，不修改 node_modules、不提交生成文件。

两个适配点必须长期保留契约：

- 原始内容混用表达式与内部定义；在自由变量/闭包分析前建立局部绑定槽，初始化仍留在原位置，保证时钟共享可变闭包和副作用顺序。
- 保持 Schemy 与此前 Web 的「操作符先求值、参数从左到右」顺序，然后一次重排已求值的调用栈进入原有 apply/TCO；不因 Scheme 标准未规定参数顺序而改变本作品的既有行为。

原始 `get-render-data`、`world-save`、`world-load!`、`node` 及所有故事规则不变。同步和异步 native 的拒绝都会结束当前求值；动态 load-file 直接由 Scheme 顺序执行，无须正则拆分内容。读档仍新建 VM，完整校验、恢复并建树后才交换活动世界。
